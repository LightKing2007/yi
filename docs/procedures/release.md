# 弈 · 开发与发布规程

| 项目 | 内容 |
|---|---|
| 性质 | 规程，强制执行；依据 [07-operations.md](../standards/07-operations.md)、[08-versioning.md](../standards/08-versioning.md)、[09-text-and-i18n.md](../standards/09-text-and-i18n.md) |
| 文件版本 | 1.1.1 |
| 修订日期 | 2026-10-03 |
| 适用范围 | 从修改代码到玩家获得新版本的全部步骤：分支、提交、PR、更新日志、发版、上线、回滚、紧急修复 |

本规程只规定操作步骤。各步骤须满足的要求以规则编号引用，规则内容以 `docs/standards/` 为准。

```
分支开发 → PR（CI 检查）→ 压缩合并到 main → npm run release → 自动打包（草稿）→ 人工确认并发布 → npm run deploy
```

## 1 分支

1.1 `main` 必须始终处于可发布状态，严禁直接在 `main` 上修改（OPS-005）。本地 `pre-push` 钩子拦截直接推送到 `main` 的操作。

1.2 每项工作从最新的 `main` 新建一个分支，分支名按 COD-021：

| 前缀 | 用途 | 示例 |
|---|---|---|
| `feat/` | 新功能 | `feat/download-page` |
| `fix/` | 缺陷修复 | `fix/back-flash` |
| `refactor/`、`perf/`、`docs/`、`test/`、`ci/`、`chore/` | 其他 | `chore/release-process` |
| `hotfix/` | 已发布版本的紧急修复（见第 7 章） | `hotfix/2.0.3` |

## 2 提交

2.1 提交说明按 OPS-001、OPS-002 书写，格式为 `类型(范围): 说明`，类型为英文，说明为中文，范围可省略：

```
feat: 安装程序下载页面
fix(联机): 返回时界面闪烁
```

2.2 各类型与更新日志的关系如下：

| 类型 | 含义 | 是否必须写更新日志 |
|---|---|---|
| `feat` | 新功能 | 必须 |
| `fix`、`perf` | 缺陷修复、性能改进 | 玩家可感知时必须 |
| `refactor`、`docs`、`test`、`ci`、`build`、`chore` | 不改变玩家可见行为 | 不写 |
| `release` | 发版（仅由发版脚本使用） | — |

2.3 联机协议不兼容的变更，在类型后加 `!`，如 `feat!: 协议 v4`，并按 VER-002、VER-003 递增主版本号。

2.4 本地 `commit-msg` 钩子检查提交说明的格式。执行 `npm install` 时自动启用 `.githooks/` 中的钩子。

## 3 PR

3.1 推送分支后创建 PR。PR 标题即合并后 `main` 上的提交说明，必须符合 OPS-001，由 CI 检查。

3.2 按 PR 模板逐项核对 [checklists.md](../standards/checklists.md) 第 1 节的检查项，不适用的项写明原因。

3.3 CI 全部通过后压缩合并（OPS-003），合并后远端分支自动删除。合并前的审查要求见 GEN-010。

3.4 合并后确认 `main` 上随之触发的 CI 通过（`gh run list --branch main --limit 1`）；失败时按 OPS-016 先修复，修复前严禁合并其他 PR。PR 上的 CI 运行在合并提交上，与推送到 `main` 时的检出方式不同，通过不代表 `main` 也通过。随后执行 `git switch main && git pull`，并删除本地分支。

## 4 版本号与更新日志

4.1 版本号只在 `package.json` 的 `version` 中定义，递增规则见 VER-002：

| 变更 | 递增位 | 示例 |
|---|---|---|
| 缺陷修复、文字修订、仅服务端的内部改进、依赖安全升级 | 修订号 | 2.0.2 → 2.0.3 |
| 新增玩家可见的功能、协议新增向下兼容的消息 | 次版本，修订号归零 | 2.0.3 → 2.1.0 |
| 联机协议或数据格式不兼容、需要强制更新 | 主版本 | 2.x → 3.0.0 |

4.2 更新日志即游戏内“更多”中的“日志”页面（`src/ui/info.ts` 的 `LOG`），按以下步骤编写：

1. 在实现功能的同一个 PR 中编写，写入最上面一节，即下一个版本的一节；该节不存在时，新建 `['H', '下一个版本号']`。
2. 每条按 I18N-070 至 I18N-073 书写，以“新增”“优化”“调整”“修复”等动词开头。
3. 每条在 `src/i18n/table.ts` 中补齐文言与英文译文，写法见 I18N-075 至 I18N-084。
4. 运行 `npm test`，`tests/text.test.ts` 自动检查译文、标点、开头动词与版本号。

4.3 GitHub Release 的发布说明由更新日志自动生成（I18N-085），严禁手工编写。

## 5 发版

5.1 前提：待发布的变更已全部合并到 `main`，更新日志最上面一节即待发布的版本。

5.2 执行：

```bash
git switch main && git pull
npm run release -- 2.0.3
```

5.3 发版脚本按 OPS-021 依次检查，任一项不满足即中止：

1. 当前分支为 `main`，工作区无未提交的变更，且与远端 `main` 一致；
2. 新版本号大于当前版本号，对应标签不存在；
3. 更新日志与译文齐全；
4. 类型检查与测试通过。

5.4 检查全部通过后，脚本修改版本号，提交 `release: v2.0.3`，创建标签 `v2.0.3` 并推送。该提交是唯一允许直接推送到 `main` 的提交（OPS-005）。

5.5 标签推送后，Release 工作流自动执行以下步骤，耗时约 5 分钟：

1. 核对标签与版本号、更新日志，并运行测试（OPS-022）；
2. 在 macOS、Windows、Linux 上分别构建安装程序；
3. 创建草稿 Release，附件为四个安装程序与服务端 `yi-server-2.0.3.cjs`，说明由更新日志生成。

5.6 人工核对草稿 Release 的附件与说明（OPS-023），确认无误后发布：

```bash
gh release view v2.0.3 --web
```

## 6 上线与回滚

6.1 Release 发布后执行上线（OPS-040）：

```bash
npm run deploy -- 2.0.3
```

6.2 上线脚本依次完成：

1. 从该 Release 下载安装程序与服务端；
2. 以安装程序替换下载页面 <http://47.108.181.240:8443/> 上的旧版本；
3. 以新服务端替换旧服务端，旧服务端保留为 `server.cjs.prev`，并将 `YI_LATEST` 改为新版本号；
4. 显示服务器当前的连接数，询问是否重启。加 `--restart` 参数时不询问，直接重启。

6.3 重启会中断正在进行的对局，必须在无活跃对局时进行（OPS-045）。整改项 P1-09 完成前，以连接数为 0 作为判断依据，并在北京时间 10:00 至 22:00 之间执行（OPS-050）。

6.4 重启后核对服务端日志首行的版本号与提交号：

```bash
ssh root@47.108.181.240 journalctl -u yi -n 1
```

6.5 新版本出现 OPS-047 所列情况之一时，立即回滚服务端：

```bash
npm run deploy -- rollback
```

整改项 P1-09 完成前，回滚只恢复服务端，安装程序与 `YI_LATEST` 须由维护者手工恢复；运维规程 `ops.md` 由整改项 P1-12 建立后，按该规程执行。

6.6 上线后按 [checklists.md](../standards/checklists.md) 第 4 节逐项核对。

## 7 紧急修复

7.1 已发布版本存在严重缺陷，且 `main` 上已有不宜发布的变更时，按以下步骤处理（整改项 P1-10 提供 `--hotfix` 参数后，以脚本代替第 3 步）：

1. 从发布标签创建分支：`git switch -c hotfix/2.0.4 v2.0.3`；
2. 修复缺陷，在更新日志中新增 `2.0.4` 一节，提交；
3. 执行 `npm version 2.0.4 --no-git-tag-version`，提交 `release: v2.0.4`，执行 `git tag -a v2.0.4 -m "弈 2.0.4"`，再执行 `git push origin hotfix/2.0.4 v2.0.4`；
4. 按第 5.5 条至第 6 章完成打包、发布与上线；
5. 24 小时内创建 PR，将修复合并回 `main`，保持 `main` 上版本号与更新日志的连续（OPS-028）。

7.2 `main` 上没有未发布的变更时，按常规流程处理：创建 `fix/` 分支，经 PR 合并后执行 `npm run release`。

## 8 仅服务端变更

8.1 服务端的变更同样经 PR 合并与发版，以发版产物 `yi-server-版本号.cjs` 上线，保证线上运行的服务端始终为某个已发布版本。

8.2 仅服务端、玩家不可感知的变更，递增修订号，更新日志写明服务器方面的改进（VER-021）。
