## 引言

本白皮书是“弈”项目全部工程规范的总纲。它的作用有三项：

1. 审查项目中已经存在的规范、约定和流程，找出反模式、模糊表述、逻辑漏洞和缺失的极端情况，并给出整改后的规定（第 5 章）；
2. 对成熟项目必须具备、但本项目尚未制定的规范，参照国际标准和国家标准从零建立（第 6 章至第 16 章）；
3. 对每一类规范给出极端与边界情况的防御要求和降级方案（第 15 章，各章亦有分散规定）。

本白皮书中的每一条规定均有唯一编号、执行等级和验证方式。凡无法量化、无法审计或无法执行的表述，均不作为规定。

## 1 范围

1.1 本白皮书规定“弈”项目在以下方面的要求：编码与命名、架构与设计、数据与存储、接口与通信、安全、质量与测试、构建部署与运维、版本与兼容、国际化与文字、极端与边界情况防御、文档、合规审计。

1.2 本白皮书适用于仓库内的全部内容，包括源码（`src/`、`server/`、`electron/`）、测试（`tests/`）、脚本（`scripts/`）、工作流（`.github/`）、构建资源（`build-res/`、`public/`）、文档（`docs/`、`README.md`、`CLAUDE.md`），以及线上服务器的部署与运维活动。

1.3 本白皮书适用于全部参与者，包括人类开发者和 AI 协作者。AI 协作者执行任何变更前必须遵守本白皮书，`CLAUDE.md` 仅作为本白皮书的入口指引。

1.4 以下内容不在本白皮书范围内：宣传片等营销素材（`trailer/`，不纳入版本控制）、第三方依赖的内部实现。

## 3 术语、定义与规范用语

### 3.1 术语和定义

GB/T 11457—2006 界定的以及下列术语和定义适用于本白皮书。

| 术语 | 定义 |
|---|---|
| 规则 | 本白皮书中带编号的单条规定，如 `COD-012` |
| 存量代码 | 本白皮书发布时（提交 `ed1cb10`）已存在于 `main` 分支的代码 |
| 新增代码 | 本白皮书发布后新建的文件，以及存量文件中新增或修改的行 |
| 棘轮 | 对存量违规数的约束机制：违规数基线记录在 `docs/audits/baseline.json`，任何变更不得使违规数增加，违规数只能减少 |
| 门禁 | 在 CI 或 Git 钩子中自动执行、不通过即阻断合并或发布的检查 |
| 外部输入 | 来自本进程以外的数据，包括网络消息、HTTP 请求、文件、`localStorage`、环境变量、命令行参数、IPC 消息、Worker 消息 |
| 活跃对局 | 服务端状态为“对局中”或“点目中”的房间 |
| 生产环境 | 线上服务器 47.108.181.240 及其上运行的服务，以及已发布给玩家的安装程序 |
| 敏感等级 | 第 8.6 节定义的数据分级 L1 至 L4 |

### 3.2 规范用语

本白皮书的规范用语与 GB/T 1.1—2020 及 RFC 2119、RFC 8174 的对应关系如下。其中“必须”“严禁”“统一”为强制要求，违反即为不合规；“允许”表示在所述条件下不构成违规。本白皮书不使用“尽量”“适度”“合理”等无法验证的表述。

| 用语 | 含义 | GB/T 1.1—2020 | RFC 2119 |
|---|---|---|---|
| 必须 | 强制要求 | 应 | MUST、SHALL |
| 严禁 | 强制禁止 | 不应 | MUST NOT、SHALL NOT |
| 统一 | 强制要求在全项目范围内采用同一做法 | 应 | MUST |
| 允许 | 在所述条件下许可 | 可 | MAY |

### 4.1 规范体系

| GEN-001 | C | 同一事项只允许在一个文件中作出规定，其他文件只允许引用该规定的编号或章节，严禁复述规定内容；`CLAUDE.md` 和 `README.md` 只保留指向本白皮书的引用 | 部分满足（F-36） |

### 4.3 存量与新增

4.3.1 新增代码必须满足本白皮书全部规则。

4.3.2 存量代码的违规按棘轮约束：违规数基线在附录 A 的 P1-01 完成时写入 `docs/audits/baseline.json`；此后任何 PR 不得使任一 B 级规则的违规数增加。

4.3.3 修改存量文件时，必须同时消除被修改函数内的全部违规，即“修改即整改”。被修改函数超过 COD-030 的长度上限时，允许另开 `refactor:` PR 整改，但必须在 14 日内完成。

### 4.4 例外

4.4.1 任何规则的例外必须在违规处以注释声明，格式统一为：

```ts
// 例外 COD-051：WebGL 扩展对象没有类型定义，在此一处转换
```

4.4.2 例外声明必须包含规则编号和不少于 8 个汉字或 4 个英文单词的原因。没有例外声明的违规一律视为不合规。

4.4.3 例外总数由 CI 统计并纳入棘轮。单条规则的例外数超过 5 处时，必须在季度审计中评估是修改规则还是整改代码。

4.4.4 等级为 A 的安全类规则（SEC 前缀）严禁以注释声明例外，确需例外时必须修订本白皮书。

### 4.6 规范的修订

4.6.1 本白皮书的修订必须通过 PR 进行，PR 标题类型为 `docs`，并在文件版本号上按语义化版本递增：新增或删除规则递增第二位，措辞修改递增第三位。

4.6.2 每次修订必须在附录 G 的修订记录中写明修订日期、版本、修订内容摘要。

4.6.3 新增 A 级或 B 级规则时，必须在同一 PR 中提交对应的执行载体，或在附录 A 中登记整改项和期限。

### 5.2 审查发现与整改

每项发现按以下格式列出：问题类型、所属对象（S1 至 S16）、问题描述、整改后的规定、改进理由。“整改后的规定”列出的规则编号即为本白皮书中替代原规定的条款。

#### 5.2.1 严重

**F-01 数据丢失：存档损坏时被静默覆盖**（S9，逻辑漏洞）

- 问题：`server/store.ts` 读取 `yi-ratings.json` 失败时，以空数据启动，异常仅以注释“第一次运行”吞掉。只要文件存在但损坏（截断、磁盘错误、手工误编辑），2 秒后的首次写盘就会以空数据覆盖原文件，全部段位永久丢失。
- 整改：DAT-050 至 DAT-053。文件不存在才视为首次运行；文件存在但解析失败时，严禁启动，必须保留原文件并以退出码 65 退出。
- 理由：遵循故障安全（fail-closed）原则。数据层的未知状态必须中止服务，而不是带着错误继续运行，参见 ISO 22301:2019 第 8.4 节。

**F-02 数据无备份**（S8，缺失）

- 问题：段位数据只有一份，存于单台服务器的单个文件。
- 整改：DAT-060 至 DAT-066。设定 RPO ≤ 24 小时、RTO ≤ 1 小时，按 3-2-1 原则保存，并定期演练恢复。
- 理由：没有备份时，任何一次 F-01 类故障、误操作或磁盘故障都会导致永久丢失，不满足 GB/T 22239—2019 第二级“数据备份恢复”的要求。

#### 5.2.2 高

**F-03 运行时组件超出支持期**（S14，过时）

- 问题：游戏随安装程序分发 Electron 38.8.6。Electron 官方只维护最新的三个主版本，当前为 42、43、44，因此 38 已不再获得安全修复。`npm audit` 报告 2 项高危漏洞，均为释放后重用。
- 整改：VER-030、SEC-060。分发的 Electron 必须处于官方支持期内，高危漏洞 30 日内修复。
- 理由：桌面端直接运行在玩家计算机上，渲染进程漏洞会危及玩家主机安全。

**F-04 服务器登录面暴露**（S8，安全缺陷）

- 问题：`sshd_config` 中为 `PermitRootLogin yes`、`PasswordAuthentication yes`，主机防火墙 UFW 未启用，仅依赖云安全组。
- 整改：SEC-040 至 SEC-044。SSH 仅允许密钥登录，主机防火墙必须启用并默认拒绝，安全组与主机防火墙双层放行同一端口清单。
- 理由：口令登录 root 是公网主机最常见的入侵途径，见 CIS Ubuntu 24.04 Benchmark 第 5.1 节；纵深防御要求两层访问控制，见 GB/T 22239—2019。

**F-05 主分支保护可被绕过**（S1，规范漏洞）

- 问题：禁止直接推送 `main` 只依靠本地 `pre-push` 钩子。`git push --no-verify` 可以绕过它，未执行 `npm install` 的克隆中钩子也不生效。免费私有仓库无法开启 GitHub 分支保护。
- 整改：OPS-005、OPS-006。CI 在每次推送 `main` 后校验提交来源：提交说明必须以 `(#PR 编号)` 结尾，或为发版脚本生成的 `release: v版本号`，否则 CI 失败并告警。同时登记决策项 D-2：升级 GitHub Pro 或公开仓库，以启用服务端分支保护。
- 理由：只在客户端执行的控制不构成有效控制，必须在服务端有对应的检测手段。

**F-06 服务进程隔离不足**（S8，安全缺陷）

- 问题：`systemd-analyze security yi` 的暴露评分为 8.3（满分 10，越低越安全）。
- 整改：SEC-045，评分必须 ≤ 4.0，并列出必须增加的 systemd 选项。
- 理由：游戏服务端直接面向公网，进程被攻破时，沙箱是阻止横向移动的最后一道防线。

**F-07 入站消息无速率限制**（S11，缺失）

- 问题：服务端只限制单条消息大小（4096 字节）和单 IP 连接数（8）。不限制单连接的消息频率，也不限制握手前的空闲时间。单个恶意客户端可以无限发送 `queue`/`unqueue`、`name` 等消息，占满事件循环。
- 整改：API-040 至 API-046，采用令牌桶限速、握手超时和违规累计断开。
- 理由：见 OWASP API Security Top 10:2023 的 API4（资源消耗不受限制）。

**F-08 明文传输身份凭据**（S11，安全缺陷）

- 问题：联机使用 `ws://`，匿名身份 `uid` 和重连令牌以明文传输，可被链路上的第三方窃取并冒用，冒用者将继承对方的段位。
- 整改：SEC-010 至 SEC-013。3.0 版本前必须切换到 `wss://`；在此之前登记为已接受风险，并且严禁在明文通道上引入账号口令。
- 理由：见 GB/T 22239—2019 关于通信传输保密性的要求，以及 OWASP ASVS 5.0 第 12 章。

**F-09 安装程序无完整性校验**（S16，供应链缺陷）

- 问题：下载页面以 `http://` 分发安装程序，未公布校验和；`deploy.sh` 从 GitHub 下载后直接上传，也不校验。
- 整改：OPS-030、OPS-031、SEC-070。发布必须生成 `SHA256SUMS`，下载页面必须展示校验和，上线脚本必须核对校验和。
- 理由：见 SLSA v1.0 关于构建产物完整性的要求。未签名且无校验和的安装程序可能被中间人替换。

### 8.6 数据分级、敏感数据加密与脱敏

8.6.1 数据统一分为四级，每一个字段在设计时必须确定其等级：

| 等级 | 名称 | 范围 | 示例 |
|---|---|---|---|
| L1 | 公开 | 其他玩家可见 | 昵称、段位、对局结果 |

### 9.3 错误码体系

9.3.1 错误码统一为 `领域.细项` 两段式字符串，领域与细项均为 kebab-case 英文。错误码一经发布，严禁改变含义或删除；废弃时只允许停止下发。

9.3.2 错误统一分为五级。每个错误码必须属于且只属于一级：

| 级别 | 名称 | 含义 | 客户端处理 | 服务端日志级别 | 是否累计违规 |
|---|---|---|---|---|---|
| E1 | 操作提示 | 玩家的操作在当前状态下不被允许，可自行纠正（如还没轮到你） | 底部提示，2 秒后消失 | 不记录 | 否 |
| E2 | 业务拒绝 | 请求合法但被业务规则拒绝（如房间已满、次数用完） | 底部提示或对话框 | `info` | 否 |
| E3 | 限流 | 超出频率或数量限制 | 提示并按 `retryAfterMs` 等待 | `warn` | 是 |
| E4 | 协议错误 | 消息格式非法、版本不符、未握手 | 版本不符时引导更新；其他情况断开并重连 | `warn` | 是 |
| E5 | 服务端内部错误 | 服务端未预期的异常 | 提示“服务器出现问题”，按 API-050 重连 | `error` | 否 |

| 编号 | 等级 | 规定 | 现状 |
|---|---|---|---|
| API-020 | A | 服务端下发的错误统一为 `{ t: 'error', code, level, params?, retryAfterMs? }`；严禁下发自然语言文本，文本由客户端按 `code` 查译文表得到（协议 v4 起执行，v3 保持兼容） | 未满足（F-17） |
| API-021 | A | 全部错误码在 `src/shared/errors.ts` 中以常量表唯一定义，每项包括错误码、级别、中文原文；本白皮书附录 B 为初始码表，新增错误码必须同时更新两处 | 未满足 |
| API-022 | A | 每个错误码必须有对应的测试用例，验证在何种条件下下发 | 部分满足 |
| API-023 | A | E5 错误严禁向客户端暴露异常消息、调用栈、文件路径；服务端日志中必须记录完整调用栈和一个错误编号 `errorId`（UUID v4），并把 `errorId` 下发给客户端，以便对照 | 不适用 |
| API-024 | A | 客户端收到未知错误码时，统一按其级别处理；级别也未知时按 E5 处理，严禁抛出异常 | 不适用 |

### 9.4 状态码与关闭码映射

9.4.1 HTTP 接口（下载页面、健康检查，以及 3.0 的 `/api/*`）的状态码统一如下，错误响应体统一为 RFC 9457 `application/problem+json`，其中 `type` 统一为 `https://yi.lightking.com.cn/errors/错误码`：

| 状态码 | 使用场景 | 对应级别 |
|---|---|---|
| 200、206 | 成功；断点续传的部分内容 | — |
| 400 | 请求格式或参数非法 | E4 |
| 401 | 未认证或令牌失效 | E2 |
| 403 | 已认证但无权限，或账号被处罚 | E2 |
| 404 | 资源不存在（含不在白名单内的文件名） | E2 |
| 405 | 方法不允许，必须带 `Allow` 头 | E4 |
| 409 | 状态冲突（如昵称已被占用） | E2 |
| 413 | 请求体超过上限 | E4 |
| 416 | 断点续传的范围无效，必须带 `Content-Range: bytes */总长` | E4 |
| 429 | 超出频率限制，必须带 `Retry-After` 秒数 | E3 |
| 500 | 未预期的服务端异常 | E5 |
| 503 | 维护中或下载并发已满，必须带 `Retry-After` 秒数 | E3 / E5 |

9.4.2 WebSocket 关闭码统一如下，严禁使用表外的关闭码：

| 关闭码 | 含义 | 客户端处理 |
|---|---|---|
| 1000 | 正常关闭（玩家离开联机页面） | 不重连 |
| 1001 | 服务端重启或维护 | 按 API-050 重连 |
| 1007 | 帧内容不是合法 UTF-8 | 不重连，写 `error` 日志 |
| 1008 | 违反策略（累计违规达到上限） | 30 秒后重连 |
| 1009 | 消息过大 | 不重连，写 `error` 日志 |
| 1011 | 服务端内部错误 | 按 API-050 重连 |
| 1013 | 服务端过载或同一 IP 连接过多 | 按 API-050 重连，首次间隔 ≥ 5 秒 |
| 4000 | 协议版本不支持 | 不重连，提示更新 |
| 4001 | 认证失败（3.0 起） | 不重连，返回登录 |
| 4002 | 同一账号在别处登录（3.0 起） | 不重连，提示 |
| 4003 | 账号被封禁（3.0 起） | 不重连，提示 |
| 4008 | 握手超时（API-042） | 按 API-050 重连 |
| 4009 | 空闲超时（`IDLE_SECS` 内无消息） | 按 API-050 重连 |

### 9.6 重连、超时与幂等

| 编号 | 等级 | 规定 | 现状 |
|---|---|---|---|
| API-050 | A | 客户端重连统一采用带完全抖动的指数退避：第 n 次重连前等待 `random(0, min(30, 1 × 2^n))` 秒；连接保持 60 秒以上后计数归零。处于对局保留期（`GRACE_SECS`）内时，上限改为 5 秒，保证保留期内至少尝试 12 次 | 未满足（F-19） |

| `ts` | 字符串 | 是 | RFC 3339 UTC 时间，精确到毫秒，如 `2026-10-02T01:42:17.123Z` |
| `level` | 字符串 | 是 | `error`、`warn`、`info`、`debug` 之一，对应 RFC 5424 的 3、4、6、7 级 |

| `errorId` | 字符串 | 否 | E5 错误的 UUID v4 |
| `err` | 对象 | 否 | `{ name, message, stack }`，仅 `error` 级别 |
