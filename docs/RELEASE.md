# 开发与发布流程

从改代码到玩家用上新版本，统一按这里的步骤走。

```
分支开发 → PR（CI 检查）→ 合并到 main → npm run release → 自动打包 → 确认发布 → npm run deploy
```

## 1. 分支

- `main` 随时可以发布，**不直接在上面改**。本地的 `pre-push` 钩子会拦住直接推送到 main 的操作。
- 每件事开一个分支，从最新的 main 拉出：

  | 前缀 | 用途 | 例子 |
  |---|---|---|
  | `feat/` | 新功能 | `feat/download-page` |
  | `fix/` | 修 bug | `fix/back-flash` |
  | `refactor/`、`perf/`、`docs/`、`test/`、`ci/`、`chore/` | 其他 | `chore/release-process` |
  | `hotfix/` | 线上版本的紧急修复（见第 6 节） | `hotfix/2.0.3` |

## 2. 提交说明

格式是 `类型: 说明`（约定式提交）。类型用英文，说明用中文，可以在括号里注明范围：

```
feat: 安装包下载页
fix(联机): 返回时界面闪一下
```

| 类型 | 含义 | 要写更新日志吗 |
|---|---|---|
| `feat` | 新功能 | 要 |
| `fix` | 修复 bug | 玩家能感觉到的要 |
| `perf` | 性能 | 玩家能感觉到的要 |
| `refactor` | 重构，行为不变 | 不用 |
| `docs` | 文档 | 不用 |
| `test` | 测试 | 不用 |
| `ci`、`build` | 自动流程、构建 | 不用 |
| `chore` | 杂项 | 不用 |
| `release` | 发版（只由发版脚本使用） | — |

联机协议不兼容时，在类型后加 `!`，例如 `feat!: 协议 v4`，这种改动要升主版本号。
本地的 `commit-msg` 钩子会检查格式。`npm install` 时自动启用钩子。

## 3. PR

1. 推送分支，开 PR。**PR 标题就是合并后 main 上的提交说明**，也要写成 `类型: 说明`，CI 会检查。
2. 按 PR 模板勾选检查项。玩家能感觉到的改动，要在同一个 PR 里写好更新日志（第 4 节）。
3. CI（类型检查、测试、构建）全部通过后**压缩合并**（squash），一个 PR 在 main 上只留一个提交，合并后分支自动删除。
4. 合并后本地 `git switch main && git pull`，删掉本地分支。

## 4. 版本号与更新日志

版本号按语义化版本，只写在 `package.json` 的 `version` 一处：

| 改动 | 版本号 | 例子 |
|---|---|---|
| 只修 bug | 改第三位 | 2.0.1 → 2.0.2 |
| 有新功能 | 改第二位，第三位归零 | 2.0.2 → 2.1.0 |
| 联机协议不兼容，必须更新才能联机 | 改第一位 | 2.x → 3.0.0 |

更新日志就是游戏里“更多 · 更新日志”那一页（`src/ui/info.ts` 的 `LOG`）。规矩如下：

- **写的时机**：做功能的 PR 里就写，写在最上面一节，也就是下一个版本的那一节。还没有这一节就新建一节 `['H', '下一个版本号']`。发版时不用再补。
- **怎么写**：按 [STYLE.md](STYLE.md) 第 4.4 条，每条以“新增”“优化”“调整”“修复”等动词开头，正式、严谨地写明改了什么。
- **译文**：每一条都要在 `src/i18n/table.ts` 里补上文言和英文，写法见 STYLE.md 第 5、6 条。

以上规矩由测试自动检查（`tests/text.test.ts`），检查项见 STYLE.md 第 9 条。GitHub Release 的发布说明由更新日志自动生成，不手工编写。

## 5. 发版

前提：要发的内容都已经合并进 main，更新日志最上面一节就是要发的版本。

```bash
git switch main && git pull
npm run release -- 2.0.2
```

脚本会依次检查：

- 在 main 上，没有没提交的改动，并且和 GitHub 上的 main 一致；
- 新版本号比现在的大，这个标签还没有；
- 更新日志写好了，译文齐全；
- 类型检查和测试通过。

全部通过后，脚本改版本号，提交 `release: v2.0.2`，打标签 `v2.0.2` 并推送。这是唯一允许直接推送到 main 的提交。

推送标签后，GitHub 上的 Release 流程会自动做这些事，大约五分钟：

1. 再核对一遍标签与版本号、更新日志，并跑一遍测试。
2. 在 macOS、Windows、Linux 上分别打安装包。
3. 建一个**草稿** Release。附件是四个安装包和这一版的服务端 `yi-server-2.0.2.cjs`，说明取自更新日志。

在网页上看一下草稿，没问题就点发布：`gh release view v2.0.2 --web`。

然后上线：

```bash
npm run deploy -- 2.0.2
```

这一步会依次完成：

- 从这个 Release 下载安装包和服务端；
- 安装包换到下载页 <http://47.108.181.240:8443/>，旧版本删掉；
- 服务端换成这一版（上一版留作 `server.cjs.prev`），服务端的最新版本号 `YI_LATEST` 改成 2.0.2；
- 显示服务器上现在的连接数，问要不要重启。重启会中断正在进行的对局，挑没人的时候。也可以加 `--restart` 不问直接重启。

重启后，旧版客户端连上时会提示有新版本，点一下打开下载页。服务端日志第一行会写出版本号和提交号：

```bash
ssh root@47.108.181.240 journalctl -u yi -n 1
```

新服务端有问题时，换回上一版：

```bash
npm run deploy -- rollback
```

## 6. 线上紧急修复

已发布的版本出了严重问题，而 main 上已经有了还不想发布的改动时：

1. 从发布标签拉分支：`git switch -c hotfix/2.0.3 v2.0.2`
2. 修好，更新日志加 `2.0.3` 一节，提交。
3. 在这个分支上发版：`npm version 2.0.3 --no-git-tag-version`，提交 `release: v2.0.3`，
   再 `git tag -a v2.0.3 -m "弈 2.0.3"`，最后 `git push origin hotfix/2.0.3 v2.0.3`。
   推送标签后照常自动打包，确认发布后 `npm run deploy -- 2.0.3`。
4. 开 PR 把修复合回 main，main 上的版本号和更新日志保持连续。

main 上没有未发布的改动时，直接按普通流程走：开 `fix/` 分支 → PR → 合并 → `npm run release`。

## 7. 只改服务端时

服务端的改动同样走 PR 和发版，用发版时打出的 `yi-server-版本.cjs` 上线，线上跑的永远是某个发布版本。
只改服务端、玩家感觉不到的修复，也照样升第三位版本号，更新日志写一句服务器方面的改进即可。
