## 1 背景

1.1 联机服务端现在把段位保存在一个 JSON 文件 `yi-ratings.json` 中（`server/store.ts`），每次段位变化整体重写。阶段 5 起要保存每一局的棋谱与段位变化明细，供反作弊、复盘与回滚查询；整体重写一个持续增长的 JSON 文件既不能按条件查询，也无法让“写入对局记录、更新双方段位、写入段位变化明细”在一个事务中完成（DAT-040）。

1.2 路线图第 1.2 节的原则：服务端继续是单文件 `server.cjs`、服务器上免 `npm install`。服务器（Ubuntu 24.04）上只有 `/opt/node` 中的 Node.js 官方二进制包。

1.3 2026-10-16 实测：

| 环境 | Node.js | `node:sqlite` 中的 SQLite | 加载时的警告 |
|---|---|---|---|
| 服务器（部署用户执行） | v24.21.0 | 3.53.4 | 无（标准错误输出为空） |
| 维护者本机 | v26.10.0 | 3.53.4 | 无 |

1.4 以项目所用的 esbuild 0.28.2 把引用 `node:sqlite` 的入口打包为 CommonJS，构建目标为 `node20` 与 `node22` 时都保留 `require("node:sqlite")`，不尝试打包；打出的文件在本机运行正常。

## 2 决策

2.1 服务端的持久化统一使用 Node.js 内置的 `node:sqlite`（同步接口 `DatabaseSync`），单文件数据库，默认位置为工作目录下的 `yi.db`（服务器上为 `/var/lib/yi/yi.db`），可由 `YI_DB` 指定（DAT-001）。

2.2 打开数据库后执行 DAT-002 规定的 PRAGMA 与完整性检查；数据库访问全部集中在 `server/db/`（DAT-044）。

2.3 服务端最低 Node.js 版本沿用 `package.json` 中 `engines` 的 `>=22.13`（`node:sqlite` 自该版本起无须命令行参数）；`scripts/build-node.mjs` 的构建目标由 `node20` 改为 `node22`，与之一致。服务器与 CI 使用 `.nvmrc` 中的 Node.js 24。

2.4 迁移期间 `yi-ratings.json` 只作为导入来源；按阶段 5 开发计划的决定 D5-1，首个数据库版本在一个版本周期内同时写入该文件，以便回滚到 2.0.7 时段位不丢，下一个版本停止写入。

## 3 备选方案

| 方案 | 不采用的原因 |
|---|---|
| `better-sqlite3` | 原生模块，须在服务器上 `npm install` 或随服务端分发与服务器的 Node.js 版本、系统匹配的二进制文件，违背单文件、免安装的原则；还要按 COD-070 新增运行时依赖 |
| 继续使用 JSON 文件，另以按行追加的文件保存对局记录 | 不能按条件查询；对局记录与段位不能在一个事务中写入，崩溃时可能出现段位已变而记录缺失 |
| 独立的数据库服务（PostgreSQL 等） | 服务器内存 1.6 GB、无交换分区（[0003](0003-server-memory-limit.md)），另起一个常驻服务的内存与运维代价与当前的玩家规模不相称 |

## 4 后果

4.1 服务端不新增任何第三方依赖，`server.cjs` 仍为单文件，上线流程不变。

4.2 `node:sqlite` 在 Node.js 文档中仍为发展中的接口。升级服务器或 CI 的 Node.js 版本时，须重新确认接口与 SQLite 版本（DAT-001 要求 ≥ 3.37），并确认加载时不输出警告；数据库访问集中在 `server/db/`，接口变化时只改一处。

4.3 同步接口的写入在事件循环中执行。写入只发生在握手、开局、终局与段位变化时，阶段 5 验收时以服务端压测核对事件循环延迟与内存（[phase5.md](../plan/phase5.md) 第 5 章）。

4.4 备份由复制 JSON 文件改为 SQLite 的在线备份（`VACUUM INTO`，DAT-062），本地与异地备份的脚本随之修改（[phase5.md](../plan/phase5.md) 第 4.8 节）。
