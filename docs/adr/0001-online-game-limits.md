# 0001 联机对局的手数与动作记录上限

| 项目 | 内容 |
|---|---|
| 状态 | 接受 |
| 日期 | 2026-10-12（#111 合并）；补录于 2026-10-14 |
| 决定者 | 项目所有者 |
| 相关 | 整改项 P2-16（审计发现 A-03）、P2-22；#111；API-046；[0003](0003-server-memory-limit.md) |

## 1 背景

1.1 服务端为每个联机房间保存整局的历史局面（悔棋、重连回放都要用），每一手保存一份完整棋盘，19 路每手约 750 字节；重连回放用的动作记录每条约 54 字节。两者此前都没有上限，一局棋可以被两名玩家以“停一手”无限刷长，单个房间的内存随之无限增长（A-03）。

1.2 动作记录原本记满 4096 条后默默停止记录，此后重连回放出的局面与实际不一致。

1.3 实施前在本机直接驱动 `RoomServer` 实测满载：1023 个 19 路房间都推到 1024 手、4096 条时，常驻内存约 1.4 GB，全体断线重连、回放消息全部积压时峰值约 1.5 GB，远超当时 `yi.service` 的 `MemoryMax=512M`。手数上限要压到 256 以下才能满足 512M，而正常的 19 路对局常有两三百手。

## 2 决策

2.1 联机对局每局至多 1024 手（`MOVES_MAX`，停一手也计入，悔棋会减少）、4096 条动作记录（`ACTS_MAX`）。

2.2 达到任一上限时按和棋结束：下发 `over`，原因沿用已有的 `draw`，随后以 `info` 说明达到的是哪一项上限；重连时随终局结果补发这条说明。

2.3 排位赛达到上限的这一局不结算段位，免得以刷手数的方式操纵段位。

2.4 写一行 `game.limit`（warn）日志。

2.5 阈值本身不足以把满载的最坏情况压进内存上限，由 [0003](0003-server-memory-limit.md) 处理。

## 3 备选方案

| 方案 | 不采用的原因 |
|---|---|
| 维持不设上限 | 单个房间可无限占用内存，属审计发现 A-03 |
| 审计建议的 2048 手 | 实测 1024 手时满载已约 1.4 GB；更高的上限只会使最坏情况更糟，而正常对局远用不到 |
| 手数压到 256 以下以满足 512M | 正常的 19 路对局常超过 256 手，会误伤真实对局 |
| 达到上限时判先达到的一方负 | 补录时整理，当时未讨论：上限由双方共同推进，难以归咎于一方，且需要新的终局原因，现有客户端无法识别 |
| 新增终局原因（如 `limit`） | 补录时整理，当时未讨论：须改协议、旧客户端无法识别；沿用 `draw` 加一条说明即可让所有客户端正确显示 |

## 4 后果

4.1 协议不变（VER-002），旧客户端照常显示和棋；英文与文言界面下，旧客户端看到的上限说明为中文原文（10-edge-cases.md 第 7 节）。

4.2 动作记录记满即结束，重连回放总是完整的，修复了 1.2 的缺陷。

4.3 单局的内存有了上限，但 1023 个房间同时被刷到上限仍约 1.4 GB；压缩对局历史登记为整改项 P2-22，按 [0003](0003-server-memory-limit.md) 暂缓。
