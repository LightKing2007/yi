| 相关 | [阶段 6、7 设计](../plan/phase6-7.md)、[下一步计划](../plan/next-development.md)；尚未提交 PR、上线或迁移生产数据 |

## 1 背景

1.1 账号采用邮箱与密码登录，注册需邮箱验证码，忘记密码只能重置。项目所有者起初提出全部保存 SHA-256 散列，以降低数据库泄露后的信息暴露；讨论后同意针对数据用途采用不同存储方式。

1.2 密码只需验证，不需恢复。普通 SHA-256 计算成本低，不能有效提高数据库泄露后的离线猜测成本；DAT-070 已规定 scrypt。公开显示名称需要恢复并显示，邮箱用于验证与找回，需要受控访问地址。仅仅散列这些字段会限制原有用途，普通邮箱散列还可被候选列表比对。

1.3 目前线上只有游客、设备、段位与对局数据库，没有密码或邮箱。此记录先确定新增账号字段的保护方向，不改变现有联机行为。

## 2 决策

2.1 密码仅存 scrypt 派生值、随机盐与受限参数：N=2^17、r=8、p=1、十六字节随机盐、六十四字节输出，格式为 `scrypt$131072$8$1$<salt-hex>$<hash-hex>`。使用异步 `node:crypto.scrypt` 和常量时间比较；不保存原密码，不提供找回原密码的接口。

2.2 密码字节原文不修剪、不规范化；输入上限在派生前检查，存储格式只接受固定参数和编码长度。昂贵派生共享有界名额，忙时拒绝，不允许无界任务或等待队列。资源上限需在目标机器测量，不能为容量而擅自降低算法参数。

2.3 公开显示名称为 L1 内容，保留可显示文本。邮箱按 DAT-072 规范化后，以 AES-256-GCM 保护地址，用独立密钥的 HMAC-SHA-256 标识查询和判重；密文版本、nonce、认证标签和密钥编号具备明确存储格式，附加认证数据绑定记录及用途，防止跨记录替换。

2.4 邮箱加密密钥与查找密钥分别保存于数据库外，不进入源代码、日志、客户端包或数据库备份。轮换与恢复须独立验证；缺失密钥、错误标签或版本不支持时明确拒绝相关操作，不降级明文保存。密文与邮箱查找标识仍按 L3 管理，不因加密而无限期保留。

2.5 本记录不批准长期邮箱保留期的例外，也不改变 DAT-070 的验证码条款。有关 DAT-074 的账号邮箱保留与短验证码的带密钥保护方案，在实施前另行形成规范修订。公开 UID 的格式、邮件服务商、游客认领依据及段位合并策略也由后续设计收敛。

## 3 备选方案

| 方案 | 处理 |
|---|---|
| 普通 SHA-256 保存密码 | 不采用；计算过快，不符合 DAT-070 |
| 可逆加密密码 | 不采用；系统无须恢复原密码，密钥泄露会暴露密码 |
| 邮箱只存散列、每次由用户输入 | 可减少可恢复地址，但不能直接按账号资料发信；本次选择受控加密地址以支持账号邮件流程 |
| 明文邮箱 | 不采用；数据库单独泄露时暴露完整邮箱 |
| 雅号只存散列 | 不采用；无法直接恢复公开显示内容 |

## 4 后果

4.1 登录仍按“对输入密码派生后比对”验证，服务端不知道原密码。scrypt 提高每次离线猜测的资源成本，但不能保证弱密码永远不会被猜中。

4.2 邮箱加密保护数据库单独泄露的场景。若运行中的服务端和解密密钥同时被控制，不能承诺邮箱仍保密；公开 UID 和雅号本来就是公开资料。

4.3 引入邮箱密钥的配置、轮换、独立备份及恢复责任。发布前必须完成实测，数据模型、隐私说明及注销流程同步更新；本记录本身不授权开通邮件服务、发送真实邮件或部署。
