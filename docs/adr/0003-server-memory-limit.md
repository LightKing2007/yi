# 0003 联机服务的内存上限与对局历史压缩的取舍

| 项目 | 内容 |
|---|---|
| 状态 | 接受 |
| 日期 | 2026-10-12（#114 合并）；补录于 2026-10-14 |
| 决定者 | 项目所有者 |
| 相关 | 整改项 P2-16、P2-22；#111、#114；SEC-045；[0001](0001-online-game-limits.md) |

## 1 背景

1.1 [0001](0001-online-game-limits.md) 设了每局的上限，但满载的最坏情况（1023 个房间同时被刷到上限）仍约 1.4 GB，峰值约 1.5 GB，超出 `yi.service` 的 `MemoryMax=512M`。

1.2 2026-10-12 在本机直接驱动 `RoomServer` 实测（19 路围棋；“刷到上限”指每局 1022 手、4095 条动作记录；峰值含全体断线重连、回放消息全部积压）：

| 场景 | 常驻内存 | 峰值 |
|---|---|---|
| 1023 个房间同时下正常的棋（每局 300 手） | 435 MB | 449 MB |
| 480 个房间被刷到上限 | 723 至 727 MB | 758 至 760 MB |
| 1023 个房间被刷到上限 | 约 1.4 GB | 约 1.5 GB |

1.3 服务器物理内存 1613 MB，没有交换分区；游戏服务以外的进程约占 500 MB。Node.js 默认的堆上限 903 MB 高于本服务可能用到的堆。

## 2 决策

2.1 `MemoryMax` 由 512M 提高到 768M，给系统留约 350 MB。

2.2 暂不压缩服务端保存的对局历史；整改项 P2-22 登记为暂缓，待玩家规模需要时实施。

## 3 备选方案

| 方案 | 不采用的原因 |
|---|---|
| 先压缩对局历史（只存每一手，局面按需重算，或增量保存），再维持 512M | 当时分析利弊后决定以后再做。补录时整理的理由：须改动服务端的核心数据结构，重新验证悔棋、重连回放与点目；以当前的玩家规模，最坏情况不会出现 |
| 把手数上限压到 256 以下 | 误伤正常的 19 路对局，见 [0001](0001-online-game-limits.md) |
| 不设内存上限 | 补录时整理，当时未讨论：违反 SEC-045；服务器没有交换分区，内存耗尽时系统会随机终止进程，可能波及 SSH |

## 4 后果

4.1 正常下棋时 1023 个房间都在上限之内；约 480 个房间同时被刷到上限时才会触及。超出时由 systemd 终止服务并在 3 秒后重启，进行中的对局全部中断（10-edge-cases.md 第 2 节“内存增长”）。

4.2 2026-10-13 随 2.0.7 上线时以 `install-service` 安装到服务器。

4.3 玩家规模增长、或出现刷手数的行为时，须重新评估并实施 P2-22；压缩后按同样的方法实测满载，须在内存上限之内。
