## 1 本版本的改动范围

1.1 自 v2.0.7 以来，随游戏或服务端运行的代码有以下改动：

- 服务端：阶段 5 的数据库、对局记录与事务内结算、配置集中校验、备份命令、按 IP 合计的加入失败次数、数据库的日志与指标（#169 至 #185）；删除旧段位存档与旧客户端的兼容（#175、#178）；`rooms.ts` 按功能拆为十余个模块（P2-12，#143 至 #152）；
- 客户端：`client.ts` 按功能拆分（#153 至 #157）、改用 `wss://`（#179）；电脑思考的选点函数拆分（#136）、规则层不再直接读时间与取随机数（#135）；更新日志与字体子集（#187）；
- 桌面版：IPC 校验发送方与窗口位置逐项校验（#126），Electron 升至 44.9.3（#182）。

1.2 渲染、特效、场景、棋盘动画与声音（`src/render`、`src/fx`、`src/scene`、`src/presentation`、`src/audio`）自 v2.0.7 无改动；`src/app` 中只有场景脚本 `scenarios.ts` 改为显式传入随机种子（#135），`src/ui` 中只有开房按钮的参数写法（#155）与更新日志的文字。

## 3 服务端（TST-045）与下载页面

3.1 同一进程中 500 条连接、共 10 000 条消息（4 次的均值）：

| 项目 | 当前 | 同一环境 2.0.7 | 变化 | TST-045 上限 |
|---|---|---|---|---|
| 单条消息处理耗时 p99（毫秒） | 0.01 | 0.01 | 0.0% | ≤ 5 |
| 单条消息处理耗时最大（毫秒） | 0.52 | 0.51 | +2.0% | — |
| 吞吐（条 / 秒，单核） | 23.0 万 | 23.3 万 | −1.3% | — |
| 测量结束时的常驻内存（MB） | 86.6 | 86.7 | −0.2% | — |
| 测量结束时的堆（MB） | 29.4 | 28.1 | +4.8% | — |

基准中的服务端使用内存中的段位存放处，不经过数据库；数据库的写入只在开局、终局与段位变化时发生，其耗时由 3.0.0 新增的指标 `yi_db_transaction_seconds` 在线上统计（07-operations.md 第 9 节）。经真实连接、写数据库的压测见第 6 章。

3.2 定时检查 `tick()`（500 名玩家）。完整基准中每次只有 20 个样本，4 次的结果为：

| | p50 | p95 | p99（即最大） |
|---|---|---|---|
| 2.0.7 | 0.03 至 0.04 | 0.08 至 0.09 | 0.22 至 0.29 |
| 当前 | 0.03 至 0.04 | 0.08 至 0.43 | 0.24 至 1.20 |

当前代码 4 次中有 3 次 p95 在 0.25 毫秒以上，超过 2.0.7 的 20%，因此加测：

- 只运行服务端的一段、`tick()` 测 300 次，交替 4 次：两者的 p50 均为 0.03 毫秒，p95 为 0.05 至 0.08 毫秒，无差别；去掉第 8 步新增的清理（`joinFailsByIp.prune`）后结果不变；
- 按完整基准的顺序（先电脑思考，再服务端）、只把 `tick()` 的样本数由 20 加到 300，交替各 2 次：

| | p50 | p95 | p99 | 最大 |
|---|---|---|---|---|
| 2.0.7 第 1 次 | 0.03 | 0.06 | 0.26 | 2.00 |
| 当前第 1 次 | 0.03 | 0.07 | 0.17 | 0.62 |
| 2.0.7 第 2 次 | 0.03 | 0.07 | 0.33 | 1.65 |
| 当前第 2 次 | 0.03 | 0.06 | 0.15 | 3.05 |

两者的 p50、p95 相同，p99 当前代码更低；两者都有零星的毫秒级单次尖峰。20 个样本时的差异，来自这类尖峰落入小样本，不是 `tick()` 变慢。下一版本起，基准中 `tick()` 的样本数宜加大，另见第 7 章。

3.3 下载页面（4 个模拟安装程序，依次请求 300 次；单位为毫秒；4 次的均值）：

| 请求 | p50 | p95 | p99 | 最大 | 同一环境 2.0.7 的 p95 |
|---|---|---|---|---|---|
| `GET /` | 0.14 | 0.28 | 0.67 | 2.29 | 0.30 |
| `GET /SHA256SUMS` | 0.08 | 0.12 | 0.25 | 0.76 | 0.12 |

## 4 渲染帧（TST-042）

4.1 本版本未重测。按第 1.2 条，渲染、特效、场景、棋盘动画与声音的代码，以及主循环所在的 `src/app`（场景脚本除外）自 v2.0.7 无改动；场景脚本只改了随机种子的传法，所测的三个局面（`renju-marks`、`gomoku-win`、`go-score`）的画面相同。联机模块的每帧检查（#156）只在联机对战中运行，不在所测的局面中。各局面的帧间隔沿用 [perf-2.0.7.md](perf-2.0.7.md) 第 4 章：p95 不超过 9.3 毫秒，满足 TST-042 对参考机 p95 ≤ 16.7 毫秒的要求。

## 6 发版前在 GitHub Actions 上运行的检查

| 工作流 | 对象 | 结果 |
|---|---|---|
| 平台冒烟检查 | `e656fab` | 通过：macOS、Windows、Linux（[运行 40099913440](https://github.com/LightKing2007/yi/actions/runs/40099913440)） |
| 服务端压测（TST-045） | `e656fab` | 通过（[运行 40099916292](https://github.com/LightKing2007/yi/actions/runs/40099916292)），见下表 |
| 服务端压测（对照） | `v2.0.7` 与 `e656fab` 前后相继各一次 | 均通过（[v2.0.7：运行 40100184696](https://github.com/LightKing2007/yi/actions/runs/40100184696)，[当前：运行 40100191629](https://github.com/LightKing2007/yi/actions/runs/40100191629)），见第 6.2 条 |

6.1 压测（GitHub `ubuntu-latest`，服务端限定在 2 核；500 条连接，每条每秒 2 条消息）。3.0.0 的服务端经数据库读写段位与对局记录（`YI_DB` 指向临时目录）：

| 项目 | 结果 | 2.0.7 报告 | TST-045 上限 |
|---|---|---|---|
| 在线连接 | 500 / 500，拒绝 0，断开 0 | 500 / 500 | 全部在线 |
| 消息处理耗时 p99 | 1 毫秒 | 1 毫秒 | ≤ 5 毫秒 |
| CPU（按单核计） | 5.5% | 5.3% | ≤ 50% |
| 常驻内存 | 166 MB | 164 MB | ≤ 256 MB |
| 事件循环延迟 p99 | 1.7 毫秒 | 1.2 毫秒 | ≤ 50 毫秒 |
| 落子往返 p99 | 0.88 毫秒（34 068 个样本） | 0.92 毫秒 | — |
| 服务端 error 级别日志 | 无 | 无 | 无 |

常驻内存 166 MB，远低于 `yi.service` 的 `MemoryMax=768M`，满足阶段 5 计划第 5.1 条第 4 项。

6.2 事件循环延迟 p99 由 2.0.7 报告的 1.2 毫秒变为 1.7 毫秒，超过 20%，落子往返也与 2.0.7 报告不同，因此在 GitHub Actions 上对 v2.0.7 与待发布的提交前后相继各运行一次压测，作同一时段的对照：

| 项目 | v2.0.7 | 当前 | 当前（第 6.1 条） |
|---|---|---|---|
| 事件循环延迟 p99 | 1.8 毫秒 | 1.6 毫秒 | 1.7 毫秒 |
| CPU（按单核计） | 9.5% | 9.1% | 5.5% |
| 常驻内存 | 162 MB | 168 MB | 166 MB |
| 落子往返 p99 | 2.13 毫秒 | 3.33 毫秒 | 0.88 毫秒 |
| 消息处理耗时 p99 | 1 毫秒 | 1 毫秒 | 1 毫秒 |

同一时段中两者的事件循环延迟、CPU 相当；v2.0.7 自身在 2026-10-06 首次实测时也为 1.7 毫秒（P2-07，#95），与 2.0.7 报告的差异来自 GitHub Actions 的运行机器。落子往返在不同的运行之间相差数倍（当前代码两次为 0.88、3.33 毫秒），不作为劣化的依据；常驻内存多 4 至 6 MB（约 3%），推测为数据库的连接与预编译语句，未单独测量。

## 7 未测项目

- TST-042 无独立显卡的 Windows 计算机上的渲染帧：需要相应的实机；
- TST-043 冷启动与渲染进程内存：需要运行打包好的桌面版；
- `scripts/bench.mjs` 的服务端段中 `tick()` 只有 20 个样本，p95、p99 易受单次尖峰影响（第 3.2 条）；加大样本数改动基准本身，留待下一版本，并以本报告第 3.2 条的结果为对照。
