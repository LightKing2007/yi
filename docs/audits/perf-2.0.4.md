## 1 电脑思考（TST-041）

1.1 五子棋：每个难度自我对弈 6 盘（固定种子，开局前两手在天元附近随机），每盘至多 60 手，统计每一手的思考耗时（毫秒）：

| 难度 | 手数 | p50 | p95 | p99 | 最大 | TST-041 上限 |
|---|---|---|---|---|---|---|
| 简单 | 159 | 0.05 | 0.25 | 0.54 | 0.81 | — |
| 普通 | 209 | 0.03 | 0.07 | 0.09 | 0.11 | — |
| 困难 | 142 | 43.6 | 143.4 | 240.7 | 269.2 | p95 ≤ 1500 |

1.2 围棋：每种路数先以简单难度走若干手得到中盘局面（9 路 12 手、13 路 24 手、19 路 40 手），再按规定的时间思考 3 手。围棋电脑按时间思考，耗时由时限决定，比较时以搜索速度（固定 2000 次模拟，每秒完成的模拟次数）为准：

| 路数 | 难度 | 思考耗时 p95（毫秒） | TST-041 上限 | 搜索速度（次 / 秒） |
|---|---|---|---|---|
| 9 | 普通 | 1200.3 | ≤ 1400 | 47 872 |
| 9 | 困难 | 3000.4 | ≤ 3200 | 36 588 |
| 13 | 普通 | 1200.6 | ≤ 1400 | 23 747 |
| 13 | 困难 | 3000.2 | ≤ 3200 | 16 791 |
| 19 | 普通 | 1202.7 | ≤ 1400 | 10 663 |
| 19 | 困难 | 3001.4 | ≤ 3200 | 8 317 |

1.3 点目估死子（19 路，走满 150 手后，3 次）：p50 15.6 毫秒，最大 15.8 毫秒。在后台线程中运行，不影响界面。

## 2 服务端（TST-045）与下载页面

2.1 在同一进程中直接驱动 `RoomServer`：500 条连接两两开好友房间（五子棋与 19 路围棋各半），每条连接发 20 轮消息（轮到自己时落子，否则心跳），共 10 000 条；每轮后调用一次 `tick()`。

| 项目 | p50 | p99 | 最大 | TST-045 上限 |
|---|---|---|---|---|
| 单条消息处理耗时（毫秒） | 0.00 | 0.01 | 1.36 | p99 ≤ 5 |
| 定时检查 `tick()`（毫秒，500 名玩家） | 0.02 | 0.12 | 0.12 | — |

- 吞吐：单核每秒约 25 万条消息（不含 WebSocket 收发与 JSON 解析）；
- 内存：测量结束时进程常驻 75.5 MB、堆 24.9 MB（含前面各项基准的残留），低于 TST-045 的 256 MB。

2.2 本测量不经网络，没有包括 WebSocket 帧处理、JSON 解析与操作系统的网络开销，也不能测量事件循环延迟。按真实连接压测须绕开 P1-05 的同一 IP 连接上限，留待 P2-07 在专门的环境中进行。

2.3 下载页面（4 个模拟安装程序，依次请求 300 次）：

| 请求 | p50 | p95 | p99 | 最大 |
|---|---|---|---|---|
| `GET /`（毫秒） | 0.21 | 0.50 | 1.12 | 2.41 |
| `GET /SHA256SUMS`（毫秒） | 0.11 | 0.16 | 0.35 | 0.80 |

单核每秒约可处理 3800 次页面请求。HTTP 请求目前没有频率限制，持续以这一速率请求即可占满事件循环（审计报告 A-04，整改项 P2-17）。

## 3 渲染帧（TST-042）

3.1 测量方法：在浏览器中以开发服务器运行游戏，窗口为 TST-042 规定的 1320×900（设备像素比 2，显示器 120 Hz）。替换 `requestAnimationFrame`，记录每帧主循环的执行耗时与帧间隔，每 100 毫秒采样一次 JS 堆，以堆的增量估算每秒新分配的内存。开发模式未压缩代码，测得的 JS 耗时略高于正式版；GPU 耗时不在主循环耗时之内，以帧间隔反映。

3.2 开始菜单（静止，默认“黄昏”光影开启，5 秒）：

| 项目 | 数值 |
|---|---|
| 帧率 | 114.4 帧 / 秒（显示器 120 Hz） |
| 主循环耗时 p50 / p95 / 最大（毫秒） | 0.1 / 0.2 / 0.6 |
| 帧间隔 p50 / p95 / 最大（毫秒） | 8.3 / 8.5 / 75 |
| 每秒新分配的 JS 内存 | 约 1.0 MB |

静止画面仍以满帧率绘制（审计报告 A-09）。帧间隔的最大值 75 毫秒为测量期间的一次停顿，p95 为 8.5 毫秒，未见持续掉帧。

3.3 对局中的典型局面：以开发用的场景脚本（`src/app/scenarios.ts`）摆出局面。场景脚本使用虚拟时钟，每帧固定前进 1/60 秒，在 120 Hz 显示器上动画以两倍速度播放，帧数与场景时间线一致。每个局面分两段统计：“动画”为场景时间线的全部帧（含从开始菜单进入对局的过渡），“停留”为时间线结束后的 360 帧（3 秒）。只统计主循环，不计 Preact 等其他回调。场景脚本在帧内同步执行的摆子与判死（正式游戏中判死在后台线程）已从主循环耗时中扣除，其中最长的一次为 15.3 毫秒。

| 局面 | 阶段 | 帧数 | 帧率 | 主循环耗时 p50 / p95 / 最大（毫秒） | 帧间隔 p50 / p95 / 最大（毫秒） | 每秒新分配 |
|---|---|---|---|---|---|---|
| 五子棋禁手标记 `renju-marks` | 动画 | 120 | 120.0 | 0.2 / 0.3 / 2.2 | 8.3 / 9.2 / 9.4 | 约 1.1 MB |
| | 停留 | 360 | 120.0 | 0.2 / 0.4 / 0.5 | 8.3 / 9.0 / 9.4 | 约 1.6 MB |
| 五子棋胜利与击散 `gomoku-win` | 动画 | 462 | 120.0 | 0.2 / 0.4 / 1.6 | 8.3 / 9.0 / 9.4 | 约 4.6 MB |
| | 停留（击散之后，复盘中） | 360 | 120.0 | 0.2 / 0.4 / 0.5 | 8.3 / 8.9 / 9.4 | 约 2.7 MB |
| 围棋点目 `go-score`（9 路） | 动画 | 330 | 120.1 | 0.2 / 0.5 / 0.7 | 8.3 / 8.9 / 9.4 | 约 5.3 MB |
| | 停留（点目结果） | 360 | 120.0 | 0.2 / 0.4 / 0.5 | 8.3 / 9.0 / 9.4 | 约 6.0 MB |
| 19 路接近满盘（直接摆 289 子） | 停留 | 360 | 120.1 | 0.2 / 0.4 / 0.5 | 8.3 / 8.9 / 9.4 | 约 7.3 MB |

3.4 结论：各局面帧间隔的 p95 不超过 9.3 毫秒，满足 TST-042 对参考机 p95 ≤ 16.7 毫秒的要求，测量期间没有掉帧。主循环的 JS 耗时 p95 不超过 0.5 毫秒，帧时间由显示器的刷新率决定。每秒新分配的内存随盘面上的棋子数增加：开始菜单约 1 MB，19 路接近满盘时约 7.3 MB（每帧约 60 KB），印证了审计报告 A-06 所列的逐帧分配。目前垃圾回收没有造成可见的停顿，但在较慢的计算机上可能引起掉帧，整改见 P2-18。TST-042 对无独立显卡的 Windows 计算机的要求（p95 ≤ 33 毫秒）本次未测。
