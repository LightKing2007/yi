## 1 本版本的改动范围

1.1 自 v2.0.6 以来，随游戏或服务端运行的代码有以下改动：

- 整改项 P2-10 收紧类型检查（#100、#102 至 #104、#106、#107）：服务端、规则、电脑思考、声音合成、渲染与特效、界面中约 667 处按下标读取的地方加了取不到值时的回退（多为 `?? 0`），属机械性改动，不改变行为；
- 服务端：未预期异常的隔离（#109）、对局的手数与动作记录上限（#111）、满员时的重连（#110）、按真实地址限流（#115）、HTTP 请求限速与下载目录缓存（#119）、下载页面的备案号（#118）、监控指标与上线后的自动检查（#92、#94）；
- 客户端：改以域名连接（#117）、服务端内部错误的提示与错误编号（#109）；桌面版启用 Electron Fuses（#98，打包时写入，不改动游戏代码）。

## 2 电脑思考（TST-041）

## 3 服务端（TST-045）与下载页面

3.1 同一进程中 500 条连接、共 10 000 条消息：

| 项目 | p50 | p99 | 最大 | 2.0.6 报告的 p99 | TST-045 上限 |
|---|---|---|---|---|---|
| 单条消息处理耗时（毫秒） | 0.00 | 0.01 | 0.87 | 0.01 | p99 ≤ 5 |
| 定时检查 `tick()`（毫秒，500 名玩家） | 0.04 | 0.31 | 0.31 | 0.12 | — |

- 吞吐：单核每秒约 21.0 万条消息（2.0.6 报告：约 26.3 万）。该指标以基准循环的总耗时为分母，含基准脚本在镜像对局中挑选落点、同步局面的时间，后者使用 `src/core` 的对局逻辑。同一环境的对照中，2.0.6 两次为 19.4 万、23.4 万，当前代码两次为 15.4 万、22.3 万，均值低 12%，在 2.0.6 自身两次相差 17% 的波动之内；单条消息的处理耗时 p99 两者均为 0.01 毫秒。
- `tick()` 的 p99 只有 20 个样本，0.31 毫秒为单个样本；对照中当前代码两次为 1.24、0.27 毫秒，2.0.6 为 0.20、0.16 毫秒，前者 1.24 毫秒的一次与同一轮中下载页面的峰值同时出现，第二轮即恢复，判断为测量时的瞬时干扰。
- 内存：测量结束时进程常驻 87.4 MB、堆 27.5 MB（2.0.6 报告：76.5 MB、25.3 MB；同一环境中 2.0.6 为 80.1 至 87.0 MB）。常驻内存含前面各项基准的残留。

3.2 下载页面（4 个模拟安装程序，依次请求 300 次；单位为毫秒）：

| 请求 | p50 | p95 | p99 | 最大 | 2.0.6 报告的 p95 |
|---|---|---|---|---|---|
| `GET /` | 0.17 | 0.34 | 0.95 | 4.17 | 0.44 |
| `GET /SHA256SUMS` | 0.10 | 0.17 | 0.45 | 1.06 | 0.14 |

单核每秒约可处理 4930 次页面请求（2.0.6 报告：约 4119）。目录列表与页面的缓存（#119）使每次页面请求省去读目录与生成页面（本机实测分别约 18、27 微秒）。基准从本机发出请求，不受按 IP 的限速影响。

3.3 经真实连接的压测（TST-045 的完整条件：2 核、500 条连接、每条每秒 2 条消息）由“服务端压测”工作流在 GitHub Actions 上对待发布的提交运行，结果见第 6 章。

## 4 渲染帧（TST-042）

4.1 方法与 [perf-2.0.5.md](perf-2.0.5.md) 第 3.1 条相同：开发服务器，窗口 1320×900，设备像素比 2，显示器 120 Hz；只统计主循环 `frame` 的回调，扣除场景脚本在帧内同步执行的步骤；每个局面从重新载入的开始菜单进入。浏览器中 `performance.now()` 的精度为 0.1 毫秒。

4.2 待发布的代码（单位为毫秒；开始菜单为静止状态 600 帧连测 3 次，局面中“动画”为场景时间线的全部帧，“停留”为其后的 360 帧）：

| 局面 | 阶段 | 帧数 | 帧率 | 主循环耗时 p50 / p95 / 最大 | 帧间隔 p50 / p95 / 最大 |
|---|---|---|---|---|---|
| 开始菜单 | 第 1 至 3 次 | 600 × 3 | 120.0 | 0.3 / 0.4 至 0.5 / 0.6 至 0.8 | 8.3 / 9.1 至 9.3 / 9.4 至 9.5 |
| 五子棋禁手标记 `renju-marks` | 动画 | 120 | 120.1 | 0.3 / 0.6 / 3.5 | 8.3 / 9.2 / 9.4 |
| | 停留 | 360 | 120.0 | 0.3 / 0.6 / 0.9 | 8.3 / 9.1 / 9.4 |
| 五子棋胜利与击散 `gomoku-win` | 动画 | 462 | 120.0 | 0.3 / 0.5 / 2.9 | 8.3 / 9.1 / 9.4 |
| | 停留 | 360 | 120.0 | 0.2 / 0.4 / 0.5 | 8.3 / 9.1 / 9.3 |
| 围棋点目 `go-score`（9 路） | 动画 | 330 | 119.3 | 0.3 / 0.5 / 0.6 | 8.3 / 9.2 / 25.1 |
| | 停留 | 360 | 120.0 | 0.3 / 0.4 / 0.6 | 8.3 / 9.3 / 9.4 |

- `go-score` 动画段帧间隔的最大值 25.1 毫秒，与 2.0.5 报告相同，为场景脚本在帧内同步判死的一帧（正式游戏中判死在后台线程）。
- 动画段主循环耗时的最大值（2.9 至 3.5 毫秒）出现在进入对局的过渡中，为单帧，与 2.0.5 报告的 4.1 毫秒相当。

4.3 同一环境中的对照：以同样的方法测 v2.0.6 的代码（导出的源码，端口 5174），各局面的帧间隔与待发布的代码相同（p95 为 8.5 至 9.3 毫秒），主循环耗时的 p50、p95 低约一个计时刻度（0.1 毫秒）。为判断这一差异，随后交替复测开始菜单（当前、2.0.6、当前、2.0.6，每轮 600 帧 2 次），主循环耗时的均值当前代码为 0.20 至 0.25 毫秒，2.0.6 为 0.21 至 0.23 毫秒，p50 均为 0.2 毫秒，两者相同；前述差异来自测量的先后与环境。

4.4 结论：各局面帧间隔的 p95 不超过 9.3 毫秒，满足 TST-042 对参考机 p95 ≤ 16.7 毫秒的要求；本版本的机械性改动（#104 等）未使渲染变慢。本次未测“每秒新分配的 JS 内存”，该项不属 TST-042 的度量，逐帧分配的整改见 P2-18。
