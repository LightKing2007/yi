## 4 必须先澄清的设计问题

### 4.1 旧草案与现行规范的冲突

| 主题 | 旧草案 | 本次规划采用的依据 |
|---|---|---|
| 口令散列 | `scrypt` 的 `N = 2^15` | DAT-070 要求 `N = 2^17`；实现前测量耗时、内存与并发，明确资源上限，不擅自降低规范参数 |
| 登录有效期 | 90 日并滑动延长 | SEC-021：最长 30 日、闲置 7 日失效；修改口令后全部会话立即失效 |
| 登录失败锁定 | 连续失败 10 次 | SEC-023：同一账号 15 分钟内失败 5 次锁定 15 分钟，同时按 IP 限速 |
| 浏览器调试令牌 | 退回 `localStorage` | DAT-083 禁止以本地存储保存机密数据；开发浏览器采用内存会话，桌面端经主进程安全保存 |
| HTTP 错误 | `{ error: code }` | API 第 4.1 条要求 `application/problem+json`；接口契约须统一 |
| WebSocket 错误 | 草案字段不完整且示例命名不一致 | API-020、API-021 的错误码、级别、参数、等待时间及 E5 的 `errorId`；覆盖未知错误码的回退 |
| 登录令牌格式 | 32 字节随机数的 base64url | API-013 现有令牌规则为 32 位小写十六进制；先区分登录与重连令牌并同步修订协议规范 |

规范表中的“现状”有历史残留，不能只凭“未满足”断定代码仍有缺陷。例如重连令牌已轮换并只存散列，集中消息校验、覆盖率工具与分层检查也已有实现。状态修订须给出对应代码或测试依据。

### 4.2 身份与数据归属

- 当前 `Player.key`、`RatingStore` 和 `GameSide` 围绕设备散列工作；`Repo.userOf()` 按设备查第一条记录。账号系统要明确区分设备、游客、会员、在线连接及持久化玩家编号，不能仅给 `hello` 增加令牌。
- 会员昵称须由账号记录决定，不能继续由游客握手中的昵称覆盖；同一设备切换账号后，段位与对局归属不得串号。
- 旧草案中的游客合并引用 `rating_changes.cause = 'import'`，而现有数据库约束已删除该取值。若决定认领数据，须设计明确的审计原因、事务与防重复认领机制，不能直接恢复旧导入代码。
- 邮箱保留与注销策略须对照 DAT-074 的敏感数据期限；活跃账号长期使用邮箱的需求与现有文字如何协调，须先形成明确规则。
- 邮件发送不能与 SQLite 同步事务绑在一起等待外网；先定义待发送、成功、失败及重试状态，确保重试不会重复消费验证码或绕过限额。

### 4.3 协议与完整恢复

- `seq` 不宜直接等于手数：悔棋会减少手数，点目标记、申请与回应可能不增加手数。建议单独定义单调递增的状态版本，并明确每类消息何时校验、何时推进，以及新局如何重新编号。
- 同步校验的范围必须明确，包括规则、棋盘、行棋方、停着状态、打劫所需历史、点目与终局等。棋盘散列不能代替服务端的身份、权限和规则校验。
- 当前 `GameRecord` 主要记录最终保留的着法，网络重连则回放 `Act[]`。替换为完整快照前，必须证明点目后恢复行棋、悔棋、申请等待、双方确认、计时、终局及段位结果均可恢复；现有 `Game` 没有草案所称的 `Match.fromRecord()`。
- 登录失效、主动退出、异地接管与普通掉线需要不同的处理；失效的会员认证不能静默退为游客并接管原会员对局。旧连接的迟到消息也不得影响新连接。
- 发出落子后应进入明确的等待确认状态；拒绝、超时、断线与重同步均须释放或重建该状态，避免连点和永久锁定。

### 4.4 HTTP、桌面端与回滚

- 当前 HTTP 接入主要是网站、下载与本机健康检查，新增账号路由须独立于静态文件处理，补齐请求体上限、内容类型、方法校验、鉴权、限流及异常隔离。
- 桌面页面使用 `app://yi/`，现有 CSP 只放行生产 WebSocket。设计账号 HTTP 请求时一并明确 HTTPS 来源、跨源预检及开发环境边界，不使用宽泛通配。
- 桌面端令牌存取经受校验的 IPC 通道，处理加密存储不可用、文件损坏、退出登录与换账号；不引入明文持久化的降级。
- 数据库迁移后，现有 `openDatabase()` 会拒绝打开高于程序支持的结构版本。4.0 回滚不能直接复用 3.0 与 3.1 之间的程序切换演练；须先验证匹配版本的数据库恢复方案，说明迁移后新增数据如何保留或处置。
- SMTP 实现、身份模块所在层及新增状态管理须符合分层表；确需新增依赖或调整依赖方向时，先完成技术评估与相应决策记录。单文件服务端是交付约束，不等同于必须手写全部外部协议。

## 6 验证要求

1. 每新增或改写一条测试，都临时破坏其所测行为，确认出现预期失败，再恢复并验证；保存变异前的内容，不以覆盖工作区的方式恢复。
2. 时间相关测试使用可替换时钟；随机行为使用固定输入。网络测试只使用本机随机端口，邮件使用实现同一接口的假发送器；真实投递另行验证。
3. 重点覆盖重复与乱序请求、并发注册、验证码重用、找回口令后旧连接、同账号接管时的迟到事件、悔棋后重同步、点目恢复、满员重连、迁移失败和结算不重复。
4. 账号与协议改动须使用真实数据库和真实 HTTP、WebSocket 的集成测试，不只验证假连接里的字段。
5. 推送前以届时 CI 的确切检查命令核对格式、棘轮、类型、覆盖率、改动行覆盖率、构建、漏洞与许可证。当前入口见 `.github/workflows/ci.yml`；本机获取远端历史不使用 `--depth`，基线比较取完整历史中的对应提交。
6. 新的检查能力用故意违规的探针验证；源码结构分析使用语法树；统计数字与独立计算交叉核对。
7. 新界面按三种语言验证排版、键盘操作与字体，加入场景及 `text-fit` 检查；正式发布前运行三平台冒烟、服务端压测及同环境性能对照。
8. 每批记录实际耗时后再制定后续安排；耗时测试按本机测量乘以 10 考虑 CI 与覆盖率开销，并符合项目的显式超时要求。
