## 1 已确认的产品行为

1.1 未登录仅可单机双人和人机对弈。匹配、排位和好友房间均须登录、邮箱验证及同意当前必需版本的相关隐私协议；客户端入口与服务端分别检查。

1.2 邮箱＋密码登录。注册表单包含用户名、邮箱、密码、邮箱验证码与协议确认。用户名作为公开显示名称，界面称“雅号”，允许重名；身份以系统分配、不可更改的公开 UID 区分。邮箱验证码只证明能接收邮件，不等于人工用户证明。

1.3 忘记密码只能通过邮箱验证码重置，不提供原密码查询。重置、修改密码均立即撤销全部登录会话和正在使用的认证连接，再要求重新登录。

1.4 允许认领升级前的游客段位与棋谱；登录不触发自动合并，设备标识不等于账号身份。具体认领保证和段位冲突规则按第 7 章决定后实施。

## 2 身份及存储边界

| 标识 | 作用 | 存储、传输及权限 |
|---|---|---|
| `users.id` | 数据库内部主键 | 现有整数主键，继续用于外键；不能作为登录凭据 |
| `public_id` | 玩家公开 UID | 新增八位 Base32 文本唯一列；不接收客户端指定或修改 |
| `devices.uid_hash` | 历史设备关联 | 保留 DAT-075 的散列；协议旧字段 `uid` 不能再混称公开 UID |
| 会话令牌 | 认证请求 | 密码学随机值；服务端仅存散列，客户端安全存储；与公开 UID 分离 |
| 联机连接与恢复令牌 | 认证后的连接及重连 | 绑定用户和会话世代；只恢复其所属对局，接管后旧连接失效 |

2.1 将账号字段放入新增的 `accounts` 表，通过 `user_id` 唯一外键与现有 `users` 一一对应，避免反复向游客行添加多个可空的机密字段。`users.kind` 继续区分历史游客与账号玩家，公开名称沿用 `users.name` 的 UTF-8 上限。所有表 `STRICT`，主键、外键、索引、长度与空值含义按 DAT-010 至 DAT-045。

2.2 `0002_accounts.sql` 已新增 `accounts` 与 `consents`，不更改已执行的 `0001_init.sql`；会话、验证码及认领审计随相应业务在后续迁移新增。账号仓储独立于现有游客仓储；会员请求直接从已认证 `user_id` 查询，不再经 `Repo.userOf(device)` 取第一条匹配记录。

2.3 账号字段包括 `user_id`、`public_id`、邮箱密文、查找标识、验证时刻、口令散列及认证世代等，准确列名与约束以 `0002_accounts.sql` 为准。加密格式版本独立保存；字段类型及长度按二进制实际大小设约束，不把密文套入邮箱明文的 254 字节限制。账号状态为 active 或 closed；注销时邮箱与凭据列必须全部为空，公开 UID 保留且不可修改。同意记录含类型、版本与时刻。

2.4 邮箱查找标识、公开 UID、会话散列分别建唯一索引；外键均声明删除策略并有前导索引。同一邮箱并发注册由数据库唯一约束裁决，不靠先查后写。雅号允许重名，不添加唯一索引，不沿用旧的 `name_lower` 唯一规则。

## 3 密码与邮箱保护

3.1 密码仅存 `scrypt$131072$8$1$<salt-hex>$<hash-hex>`。参数为 DAT-070 的 N=2^17、r=8、p=1；随机盐 16 字节，派生值 64 字节。使用异步 `node:crypto.scrypt`，比较使用 `timingSafeEqual`，严格限制持久化参数和编码长度，不允许数据库中的任意参数控制派生资源。不修剪或规范化密码，注册与登录使用相同 UTF-8 内容；产品最低长度由 HTTP 校验层负责，底层另设字节上限。

3.2 认证服务共享一个有界的密码任务执行器，不按请求新建实例。入口先做请求体、邮箱、验证码及频率检查，再占用任务名额；忙时明确返回可重试错误，不无限排队。缺失账号的登录也须采用固定允许格式的虚拟密码散列执行验证，避免通过是否执行昂贵计算直接区分账号存在性。对真实存在账号与虚拟账号同样限流。

3.3 本机可行性试跑不代表服务器容量。Node 默认 `maxmem` 无法运行上述参数，必须显式配置；并发、堆外内存、事件循环延迟及对游戏消息的影响要在目标服务器同配置下测量，保持原算法强度。当前基础模块采用单任务、无等待队列，不据此承诺吞吐量。

3.4 邮箱先按 DAT-072 小写及 NFC 规范化，校验后生成两个独立表示：AES-256-GCM 密文供受控发信；HMAC-SHA-256 查找标识供登录及唯一约束。查找密钥与加密密钥独立，均在数据库外提供，只由配置入口装配；不进入源代码、日志、游戏包或数据库备份。

3.5 加密采用每次随机 nonce、完整认证标签及密钥编号。注册前还没有账号 ID，挑战邮箱以格式版本、用途与随机挑战编号作为附加认证数据；注册成功后重新加密为绑定用户 ID 的账号邮箱，并删除挑战中的地址副本。附加认证数据绑定格式版本、字段用途与不可变的内部账号标识；密文被换到其他账号或任意字段被修改时拒绝解密。没有有效密钥或标签验证失败时关闭相关账号操作，严禁降级为明文。登录仅查 HMAC 索引，不扫描、逐个解密全部邮箱。

3.6 密钥轮换需保留读取旧密文的密钥，后台重加密后再撤除旧密钥；查找密钥轮换须有带版本的双索引迁移和并发唯一性方案，不能简单换密钥后导致同邮箱重复注册。数据库和密钥分别加密备份并演练恢复；只有数据库泄露时，邮箱密文与带密钥查找标识提供额外保护，服务端运行权限和密钥同时失守时不承诺邮箱仍保密。

3.7 雅号为 L1 公开内容，保留可显示文本。邮箱密文与查找标识仍按 L3 管理，密码散列、验证码凭据和会话散列按 L4 管理。日志不记录密码、验证码、密钥、令牌、完整请求体或邮箱查找标识；邮箱只允许规定的脱敏形式。

3.8 项目所有者已同意绑定邮箱在账号存续、目的仍为登录、验证和密码重置时保留，DAT-074 已同步修订。未完成注册、过期挑战及其他 L3 按更短期限清理；注销十五日内清除邮箱、查找标识及认证凭据并匿名化棋谱。不可变备份自然淘汰，恢复后须重放删除记录再开放服务，见决策 0011；注销与备份恢复尚待实现。

## 4 验证码与邮件边界

4.1 验证码按用途隔离：注册、重置密码、更换邮箱。挑战具有独立随机编号、邮箱查找标识、用途、到期时间、尝试次数与发送状态；成功仅能消费一次。重新发送使旧挑战失效，原子增加错误次数，过期或次数耗尽后不能再次验证。挑战编号本身不是通过验证的证明。

4.2 旧草案的六位数字、十分钟、五次尝试、邮箱六十秒冷却及每日十次发信暂作为防滥用策略候选，不是实测容量。验证码查验、IP 与邮箱发信限额、全局发送预算均在昂贵密码派生之前执行；计数和限额所用时间经可替换时钟读取。登录限流采用现行 SEC-023：账号十五分钟五次失败锁十五分钟，IP 每分钟至多十次。

4.3 短数字验证码空间小，普通 SHA-256 不能阻止数据库泄露后的离线枚举。采用独立密钥 HMAC-SHA-256 绑定用途、挑战编号、邮箱查找标识与验证码，DAT-070 已同步修订；高熵会话令牌继续只存 SHA-256。相关密钥与状态机制完成验证后再接入持久化。

4.4 发信在数据库事务外执行。持久化待发送任务不保存可还原的验证码；发送进程生成验证码、持久化其验证凭据后执行受时限控制的发送。进程崩溃或超时导致交付状态不明确时，不无限重发同一凭据，而是标记需重发，由受限额约束的新挑战替代；客户端从明确的重试提示恢复。邮箱地址只在规范化及实际发送时短暂解密。挑战的发送状态区分 `queued`、`sending`、`sent`、`unknown`、`failed`；只有当前代际且发送成功的挑战允许核验，发送状态不明时引导受限额约束的重发。状态更新带挑战编号与代际条件，新挑战替换后，旧发送任务的迟到成功、失败或超时不能复活旧凭据、覆盖新状态。

4.5 SMTP 或邮件 API 通过可替换接口注入；测试使用假发送器，真实投递单独验收。发送失败计入限额，不能被用来绕过限流。重置与发码响应避免透露账号是否存在；错误文案、返回结构和可观察流程一致，发信异步处理。邮件服务商、费用、域名验证与真实发送尚未决定，不在本批开通或发信。

## 5 HTTP、会话与同意记录

| 接口 | 语义与主要限制 |
|---|---|
| `POST /api/code` | 用途与邮箱校验、请求及发送限额、统一接受响应；返回非认证性质的挑战编号 |
| `POST /api/register` | 表单名称、邮箱、密码、挑战编号、验证码与协议版本；先验证再派生密码，最终事务中复查并消费挑战、写账号和同意记录，失败不部分注册 |
| `POST /api/login` | 邮箱＋密码；返回会话与玩家资料；客户端不得指定服务端用户编号或通过设备字段替代认证 |
| `POST /api/logout` | 撤销当前会话，立即终止使用它的认证连接 |
| `POST /api/password/reset` | 验证重置挑战、写新密码并原子撤销全部会话；不查询原密码 |
| `POST /api/password/change` | 已认证且验证旧密码；成功后撤销全部会话 |
| `GET /api/me` | 当前雅号、公开 UID、邮箱验证与同意状态、段位；不返回密码凭据、邮箱密文、密钥或邮箱查找标识 |
| `POST /api/consents` | 明确提交必需协议的版本及同意动作，服务端记录时刻；不能仅依赖客户端布尔值 |
| `POST /api/me/name` | 修改雅号，重新校验文本；不改变 UID |
| `DELETE /api/me` | 重新认证、撤销会话、禁止联机，并进入限期匿名化流程 |

5.1 统一 HTTPS、JSON、请求体和字段大小上限、方法与来源校验；错误为 API 第 4.1 条的 `application/problem+json`，复用错误码、参数及重试等待时间，不返回堆栈与机密字段。限额、任务过载和发送不可用各有可恢复语义。

5.2 会话最长三十日，闲置七日失效（SEC-021）；客户端轮询不得无限刷新绝对期限。验证、注销、接管和定时清理共用同一撤销路径；撤销时让内存连接立即失效，不能只等下次握手查询。公开 UID 从账号记录返回，不能从设备标识推断。

5.3 同意记录至少包含用户、协议类型、版本与同意时刻。服务端维护必需版本；新必需版本未同意时阻止新匹配和进入房间，现有对局的处置在接口定稿时明确，避免在对局中途静默变更规则。登录、邮箱验证、同意状态均来自服务端。

5.4 桌面令牌只经受校验 IPC 保存到主进程的 `safeStorage` 加密文件；加密不可用或文件损坏时回到未登录状态，不写明文。浏览器调试仅内存会话。CSP 与 CORS 精确允许生产 HTTPS 来源及桌面 `app://yi/`，本机调试单独配置，不开放通配来源。

## 6 公开 UID 与雅号

6.1 显示名称称“雅号”，允许重名；公开 UID 是唯一且不可更改的账号标识，查找与举报使用 UID，展示时配合雅号。称呼、重名规则与 UID 格式均已由项目所有者确认。

6.2 UID 为八字符文本：七位密码学随机 Base32 数据加一位 Luhn mod 32 校验字符，字母表为 `0123456789ABCDEFGHJKMNPQRSTVWXYZ`，排除 I、L、O。规范值大写，允许小写输入及四位之间的单个连字符；例如存储 `7KM4P9D2`，显示 `7KM4-P9D2`。不含日期、生日、地区、邮箱或密码，不转换为整数。

6.3 校验只用于发现录入错误，不能用于认证，也不保证检出所有换位。独立试算及测试确认示例有效，全部二百四十八种单字符替换均不通过。客户端与服务端共用 `src/shared/publicId.ts`，随机生成仅在 `server/publicId.ts` 使用密码学随机源。

6.4 数据库唯一索引裁决碰撞，有限重试后明确失败，不把随机数当作绝对唯一。公开 UID 与数据库内部主键分离，不能用公开 UID 直接认领游客数据或恢复登录。完整决定见 [0011](../adr/0011-public-id-and-account-retention.md)。

## 7 旧游客数据认领

7.1 现有设备标识是客户端提交的标识，不提供强所有权证明。不能把“知道设备标识”解释为原账号认证。先查明升级前是否能建立服务端签发、绑定设备且单次使用的认领凭据；无法证明所有权的存量记录保留，采用项目所有者明确接受的人工或低保证流程，不自动放开认领。

7.2 建议每种棋的游客段位只允许导入尚未开始该棋排位的新账号；已有排位时不直接相加或取高分，棋谱可通过独立的别名归属关联保留。此为候选，需决定后实现。认领需要当前账号登录、邮箱验证、所需同意及一次明确动作。

7.3 单事务记录原游客、目标账号、依据、时间及结果；原游客只可被认领一次，重复请求返回同一结果，并发请求不能给两个账号。历史对局与段位变化保留可追溯关系，不批量重写历史双方外键、不生成现有约束禁止的 `cause='import'`；新的审计原因、认领别名与查询均由迁移明确定义。认领期间不能存在仍待结算的游客对局。

## 8 协议第 4 版与状态恢复

8.1 `hello` 携带账号会话，已认证身份与连接绑定。无效或失效认证明确拒绝，不降级游客。握手后按用户关联段位与对局，单账号只允许一条有效联机连接；新连接接管先使旧连接世代失效，再恢复同一对局，旧连接迟到的落子和关闭事件不得影响新连接。

8.2 不把手数当作状态版本。每局使用独立 `matchId` 与单调 `stateVersion`，每次服务端提交的可观察对局变更推进版本；悔棋、停一手、点目、申请及回应等也纳入。幂等请求另外携带请求编号，重复编号不二次执行，版本冲突返回完整同步；具体消息字段与错误码在协议模块实现前写出逐消息对照表。

8.3 完整恢复须覆盖规则配置、棋盘、行棋方、打劫及历史、停着状态、双方时钟、点目、申请等待、终局及段位结算标识。当前 `GameRecord` 不能直接替代 `Act[]`；先建立等价恢复测试，证明与服务端状态一致，再切换快照。禁止引用不存在的 `Match.fromRecord()`。

8.4 联机输入保持服务端确认后落子，等待状态在确认、拒绝、掉线、重同步与退出时均可释放或重建。版本或快照摘要仅用于同步检查，权限和规则继续由服务端校验。协议切换须配套客户端、服务端、解析器和更新提示；更新资源实际可下载后才指引旧客户端升级。

## 9 分批验证与回滚

9.1 先交付不接入现有流程的密码、邮箱保护及公开 UID 基础模块，并完成密码资源可行性测量。其接口独立于邮件商，允许在第 10 章待定事项期间完成；不表示已开放账号功能。账号及同意记录仓储已完成基础实现；随后依次完成会话与验证码仓储、认证业务、HTTP 与邮件、桌面界面及协议配套切换，遵循 [下一步计划](next-development.md) 第 5 章。

9.2 每条新增测试都临时破坏被测行为，观察对应断言失败并恢复原文；涉及时间、异步名额与限额的验证用可替换时钟或确定性可控任务。真实密码散列与独立实现交叉核对，不在测试中断言运行必须多快。集成覆盖真实数据库、HTTP、WebSocket，以及同一设备换账号、撤销中途连接、并发注册和认领。

9.3 迁移先在生产备份副本测试，验证新建、升级、重复启动、约束、失败回滚及查询计划。迁移后旧程序会拒绝打开高版本数据库；回滚必须使用匹配版本的数据库与密钥备份，明确迁移后新增账号与对局的保留方案，不照搬 3.0 到 3.1 的二进制切换演练。

9.4 上线前验证密钥缺失、密钥错误、备份恢复、邮件不可用、密码任务过载、客户端加密存储不可用，以及游戏消息在认证压力下的性能。完成同环境基准比较和三平台验证后再进入阶段 8 与发布验收；本次不进行部署或真实投递。

## 11 技术依据

密码方案依据 DAT-070 与 [OWASP 密码存储指南](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html)。异步 scrypt、内存限制与常量时间比较接口见 [Node.js 24 crypto 文档](https://nodejs.org/docs/latest-v24.x/api/crypto.html)。邮箱加密与密钥分离参考 [OWASP 加密存储指南](https://cheatsheetseries.owasp.org/cheatsheets/Cryptographic_Storage_Cheat_Sheet.html)。这些依据支持技术选型，不代表已经完成服务器容量、法律文本或真实邮件投递验收。
