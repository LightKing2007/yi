## 1 范围与目标

1.1 本文件把 [roadmap.md](roadmap.md) 第 5 章“阶段 5：数据库、对局记录与服务端加固”分解为可逐个合并的步骤，写明每一步的内容、依据的规则、前后依赖与验收方式。路线图第 5 章规定“做什么”，本文件规定“按什么顺序、以什么标准做”。

1.2 阶段 5 完成时须达到以下结果：

1. 服务端以 `node:sqlite` 单文件数据库取代 `yi-ratings.json`，段位、对局记录、段位变化明细均入库；
2. 每一局联机对局的棋谱（含每手用时）从上线之日起积累，供阶段 8 的反作弊与阶段 9 的复盘使用；
3. 排位结算在一个事务中完成，结算前从数据库重新读取段位（DAT-040，原问题 A8 中的覆盖问题）；
4. 数据库的迁移、备份、恢复与回滚有成文的流程与测试，生产数据的 RPO ≤ 1 小时（DAT-060）；
5. 联机协议仍为第 3 版，客户端不需要更新。

1.3 下列事项不在阶段 5 内：账号、会话令牌、邮箱验证码（阶段 6）；协议第 4 版与错误码体系 P2-03（阶段 7）；举报、处罚、管理工具（阶段 8）；TLS 与 CSP 收紧 P2-05（随下一个客户端版本或阶段 4）。

### 4.2 第 1 步：准备

4.2.1 `tests/server.test.ts` 按功能拆为若干文件（握手与重连、配对、房间、对局、段位、维护模式与上限等），整段搬移，以脚本逐行核对搬移前后（总则第 4.3.3 条的例外）。阶段 5 会大量改写其中与段位存放处相关的部分，先拆分可使后续 PR 的差异集中。

4.2.2 架构决策记录 0008 写明：采用 `node:sqlite` 的理由（免 `npm install`、同步接口适合单进程服务端）、备选方案（`better-sqlite3` 需要原生模块；继续使用 JSON 文件无法支持对局记录的查询）、后果（服务端最低 Node.js 版本、`ExperimentalWarning` 的处理、服务端构建目标）。

4.2.3 只读核实服务器上 `/opt/node/bin/node --version` 与 `node:sqlite` 中 `sqlite_version()` 的结果（DAT-001 要求 SQLite ≥ 3.37，STRICT 表自 3.37 起支持）。服务器的只读检查须由项目所有者执行或授权。

### 4.3 第 2 步：修订表结构（P2-01）

4.3.1 修订 [roadmap.md](roadmap.md) 第 5.2 节，使其符合 [03-data.md](../standards/03-data.md)，范围按 D5-3 的决定。逐项落实：

1. 全部表声明 `STRICT`（DAT-020）；时间列为 UTC 毫秒并以 `_at` 结尾（DAT-012）；
2. 布尔列以 `is_` 开头并带 `CHECK`（DAT-013）；枚举列为 kebab-case 文本并带 `CHECK`，棋类由 `game_type INTEGER` 改为 `TEXT CHECK (game_type IN ('gomoku', 'go'))`（DAT-016）；
3. 避开保留字：`meta` 表的 `key`、`value`，`rating_changes` 的 `before`、`after`、`at` 改名（DAT-014）；
4. 文本列带长度上限（DAT-022），允许为空的列注明空值的含义（DAT-023）；
5. `games.record` 带 `CHECK (json_valid(record))`，内容为 `{ "v": 1, …GameRecord }`，单值 ≤ 256 KB（DAT-024）；按 API-046 的上限（1024 手），19 路一局的棋谱约在此范围内，须在第 6 步实测确认；
6. `flags` 改为子表 `game_flags`（DAT-025），本阶段只建表、不写入；
7. 外键声明 `ON DELETE RESTRICT`（DAT-030），每个外键列有索引（DAT-031），索引按 `idx_`、`uq_` 命名（DAT-015）；
8. 每个字段标明数据等级 L1 至 L4（03-data.md 第 6.1 条）；
9. 写明对局记录中悔棋的处理：棋谱只保存终局时的着法序列，悔棋等动作是否另存，在本步确定。

4.3.2 本步只改文档；DDL 在第 4 步以迁移文件 `server/db/migrations/0001_init.sql` 实现。

### 4.4 第 3 步：配置模块（P2-04）

### 4.5 第 4 步：数据库的打开与迁移（P2-02 的前半）

4.5.1 新增 `server/db/index.ts`：打开数据库后执行 DAT-002 规定的 4 条 PRAGMA；`PRAGMA integrity_check` 结果不为 `ok` 时拒绝启动；数据库结构版本高于程序支持时拒绝启动，严禁写入（VER-012）。

4.5.2 迁移框架：按 `meta` 表中的结构版本顺序执行 `migrations/NNNN_描述.sql`，每个迁移在一个事务内执行，可重复执行（DAT-041）；执行前以 `VACUUM INTO` 备份到 `/var/lib/yi/backup/pre-migrate-版本号-时间.db`，失败时回滚事务并拒绝启动（DAT-042）。迁移文件随服务端打包进 `server.cjs`，保持单文件。

4.5.3 `scripts/build-node.mjs` 的构建目标改为 `node22`，确认 esbuild 把 `node:sqlite` 视为内置模块而不打包。

4.5.4 测试：新增 `tests/db.test.ts`，以 `:memory:` 与临时目录中的文件数据库覆盖迁移的顺序、重复执行、失败回滚、结构版本过高、完整性检查失败、迁移前备份。

### 4.6 第 5 步：仓储与段位（DAT-044）

4.6.1 新增 `server/db/repo.ts`：全部 SQL 集中于此，预编译一次、参数绑定（DAT-045）；业务模块只经接口访问。`RatingStore` 接口保留，以数据库实现取代 `FileStore`；`MemoryStore` 继续供测试使用，或改为 `:memory:` 数据库。

4.6.2 每个完成握手的 `uid_hash` 对应一个 `kind = 'guest'` 的用户，写入设备表（路线图第 5.4 节）。

4.6.3 导入 `yi-ratings.json`（路线图第 5.6 节）：数据库为空且找到该文件时，在一个事务内导入全部记录，每条写一行 `cause = 'import'` 的段位变化；成功后原文件改名为 `yi-ratings.json.imported`。按 D5-1 的决定，不改名，继续双写，至下一个版本停止。导入时逐条校验，校验失败的记录写 `warn` 并跳过、原文件不动（10-edge-cases.md 第 4 节）。

4.6.4 测试：导入的条数与段位逐条核对；导入中途失败时数据库为空、原文件不变；重复启动不重复导入；含 `__proto__` 键的记录正确导入（A-15 的回归）。

### 4.7 第 6 步：对局记录与结算

4.7.1 每局开局时写入对局表（双方、棋类、路数、规则、开始时刻），终局时在一个事务内写入棋谱、结果与终局原因、双方段位、段位变化明细（DAT-040）。结算前从数据库重新读取双方段位，不再使用握手时缓存的值。

4.7.2 每手用时：轮到一方时记下 `ctx.now()`，收到该方的落子或停一手时把差值写入 `MoveRec.ms`；悔棋后的处理按第 2 步的决定。

4.7.3 数据库写入失败（约束违反、磁盘写满）时回滚事务，写 `error` 日志，向双方下发 E5，本局不计段位并说明（10-edge-cases.md 第 4 节、EDGE-002 的“故障即停”）；其余对局照常进行（P2-15 的异常隔离）。

4.7.4 对局表与段位表上的热路径查询，在 PR 中附 `EXPLAIN QUERY PLAN` 的结果（DAT-032）。

4.7.5 测试：一局匹配、一局排位、一局好友对局终局后的记录逐字段核对；棋谱可由 `replay()` 回放到终局局面；结算事务中途失败时段位与对局记录均不变；两局同时结算同一玩家时段位不被覆盖。

### 4.8 第 7 步：备份（P2-02 的后半）

4.8.1 服务端新增 `node server.cjs backup`：以 `VACUUM INTO` 生成一致的快照（DAT-062），附 SHA-256 校验和（DAT-064）。`scripts/server/backup.sh` 改为调用该命令；`yi-backup.timer` 由每日改为每小时（DAT-060 的 RPO ≤ 1 小时），本地保留份数按服务器磁盘的实测余量确定，并保持 DAT-061 的“每日一份、保留 7 份”。

4.8.2 `scripts/offsite.ts` 改为上传数据库快照；对象命名、生命周期规则与加密方式不变（DAT-063）。按 D5-1 的决定，双写期间同时备份 JSON 文件。

4.8.3 上线新版本后按 DAT-065 演练一次恢复：从异地备份下载、解密、`integrity_check`、核对条数与校验和，结果记入 `docs/audits/`。

4.8.4 改动 `yi-backup.timer`、`yi-offsite.service` 须经项目所有者同意，以 root 执行相应的安装命令（SEC-044）。

### 4.9 第 8 步：按 IP 统计加入房间的失败次数

4.9.1 加入房间的失败次数改为按连接的真实 IP 统计（`server/clientIp.ts` 的取法），重新连接不清零，与现有按连接的限制并存（API-044、原问题 A6）。统计只在内存中进行，定期清理过期的计数，避免内存随 IP 数增长（D5-4）。

## 6 风险与对策

| 风险 | 对策 |
|---|---|
| 导入或迁移失败导致无法启动 | 迁移前自动备份（DAT-042）；失败时拒绝启动而不写坏数据（EDGE-002）；上线脚本健康检查失败自动回滚（OPS-046） |
| 回滚后段位丢失 | 按 D5-1 处理；上线前手工备份（DAT-066） |
| `node:sqlite` 仍标为实验性，接口在 Node.js 升级时变化 | 架构决策记录 0008 中记录；数据库访问集中在 `server/db/`（DAT-044），变化时只改一处；CI 以 `.nvmrc` 的版本运行测试 |
| 同步写入阻塞事件循环 | 写入只在开局、终局与段位变化时发生；以压测核对事件循环延迟 p99 |
| 服务器内存与磁盘有限（1.6 GB 内存、无交换分区） | 第 5 章第 4 项实测内存；备份份数按磁盘实测余量确定；对局记录的增长量在上线一周后统计 |
| `integrity_check` 随数据库增大而变慢，影响 OPS-046 的 30 秒时限 | 第 4 步测量耗时；超出时改为 `quick_check` 并在架构决策记录中说明 |
