本契约定义批次 F 的联机协议第 4 版：握手改用账号登录、对局与段位归属账号、同一账号只保留一条联机连接、错误与提示统一为错误码、对局状态带版本号以便发现并修复不同步。它是 [阶段 6、7 设计](phase6-7.md) 第 10 章“逐消息契约、完整快照结构和现有对局的协议更新策略”一项的定稿稿。实现以本契约为准；本契约不改变 WebSocket 传输、消息大小、限流与心跳的现有规定（API-001 至 API-003、API-040 至 API-051）。

## 1 原则

1.1 第 4 版与第 3 版不兼容，随 4.0 发布，按 VER-002 递增主版本。服务端不同时支持第 3 版：按 VER-010 中主版本立即强制更新的规定，在发布说明中写明须更新（决策 0009 只针对 3.0 的升级，[路线图](roadmap.md) 第 4 章写明它不适用于账号升级，此处不以它为依据）；第 3 版客户端只收到更新指引（第 8 章）。

1.2 身份只来自服务端核验过的登录令牌：客户端不再上报昵称与本机匿名标识 `uid`，服务端不再按设备散列查找段位（[阶段 6、7 设计](phase6-7.md) 第 8.1 条）。

1.3 服务端仍是对局状态的唯一可信来源（ARC-031）。状态版本只用于发现不同步并触发完整同步，权限与规则仍由服务端逐条校验。

1.4 消息类型、字段与取值继续只在 `src/shared/protocol.ts` 定义（API-005），由 `src/shared/parse.ts` 的 `parseC2S`、`parseS2C` 校验（API-010、API-016）。

## 2 与第 3 版的主要差别

| 方面 | 第 3 版 | 第 4 版 |
|---|---|---|
| 握手 | `hello` 带昵称、本机 `uid`、可选重连令牌 | `hello` 带登录令牌、可选重连令牌，不带昵称与 `uid` |
| 身份与段位 | 按 `uid` 散列找到游客，段位跟着设备 | 按账号（`users.id`）找段位与对局；游客数据保留，留待游客认领 |
| 显示名称 | 玩家自填昵称，可随时以 `name` 修改 | 账号的雅号；`name` 消息取消，改雅号走账号接口，下一局起生效 |
| 同时在线 | 同一设备可开多条连接 | 同一账号只保留一条连接，后来的接管，先前的以 4002 关闭 |
| 退出、改密 | 无关 | 账号的登录被撤销时，其联机连接以 4001 立即关闭 |
| 错误与提示 | `error`、`info`、`unmatched.reason`、`joinNo.reason` 下发中文文本 | 一律下发错误码（API-020），客户端查译文表显示 |
| 达到对局上限 | 终局原因为 `draw`，另以 `info` 说明 | 专门的终局原因 `limit-moves`、`limit-acts`（API-046） |
| 状态同步 | 重连时回放；没有版本号，无法发现丢失的消息 | 每局有编号与状态版本；请求带序号，重复请求不二次执行；发现不同步即完整同步 |

## 3 握手与身份

### 3.1 `hello`

```json
{ "t": "hello", "v": 4, "auth": "<登录令牌>", "resume": "<重连令牌，可选>" }
```

| 字段 | 规则 |
|---|---|
| `v` | 整数，必须为 4；其他值按第 8 章处理 |
| `auth` | 账号接口签发的登录令牌，32 位小写十六进制（与契约第 3.6 条一致） |
| `resume` | 上次 `welcome` 下发的重连令牌，32 位小写十六进制；没有时省略 |

3.1.1 服务端按以下顺序检查，任何一步失败即发送错误并关闭连接，不降级为游客：

| 顺序 | 检查 | 失败时 |
|---|---|---|
| 1 | 消息格式与版本（`parseC2S`） | 第 8 章；格式错误按 API-015 |
| 2 | 账号功能已开启（`YI_ACCOUNTS`） | `server.maintenance`（E2），关闭码 1001 |
| 3 | 登录令牌有效：会话未过期、未撤销，认证世代与账号一致 | `auth.invalid`（E4），关闭码 4001 |
| 4 | 联机资格：邮箱已验证、已同意当前必需版本的协议 | `consent.outdated`（E2），关闭码 4001 |
| 5 | 该账号未因累计违规被暂时拒绝（API-045，改按账号计） | `rate.limited`（E3），关闭码 1008 |
| 6 | 带 `resume` 且找到该账号的掉线会话：回到原来的会话（第 4.2 条） | 找不到时按新连接处理，并补发 `resumeFailed` |
| 7 | 玩家数上限（API-046）：只限制新上线的账号，接管与重连不占新名额 | `server.full`（E2），关闭码 1013 |

3.1.2 第 3、4 步调用同一认证业务（`Authentication`），在握手时同步完成，并更新会话的活动时间（闲置期限从此重算，绝对期限不变，SEC-021）；不发起网络请求。协议版本更新须重启服务端，因此握手时的联机资格检查即覆盖整条连接的期间；对局中途不因新版本协议而打断。

3.1.3 连接记住所用登录会话的编号与绝对期限。会话不能靠联机延长到期限之后（SEC-021）：服务端在每秒的定时检查中，以 `auth.invalid`（E4）关闭已过绝对期限的连接（关闭码 4001），处理同第 4.3 条；连接期间每小时至多一次更新会话的活动时间，使正在联机的会话不因闲置期限失效。会话被撤销时立即关闭，不等定时检查（第 4.3 条）。

### 3.2 `welcome`

```json
{ "t": "welcome", "id": 17, "resume": "<新的重连令牌>",
  "user": { "publicId": "7KM4P9D2", "name": "黑白" },
  "ratings": { "gomoku": { "points": 1200, "win": 0, "loss": 0, "draw": 0 }, "go": { "…": "…" } },
  "latest": "4.0.1", "url": "https://yi.lightking.com.cn/download/" }
```

| 字段 | 规则 |
|---|---|
| `id` | 本次服务端运行中的玩家号，只用于日志与界面对照，不是账号标识 |
| `resume` | 重连令牌，与第 3 版的 `token` 相同的签发与作废规则（SEC-020、SEC-022），改名以免与登录令牌混淆 |
| `user` | 公开 UID 与雅号，只含契约第 4 章白名单中的这两项 |
| `ratings` | 该账号两种棋的段位；账号从未排位时为起始段位 |
| `latest`、`url` | 同第 3 版，服务端配置了才有 |

## 4 一个账号一条连接

4.1 服务端以账号的内部编号索引在线玩家。新握手的账号已有在线连接时，由新连接接管：先使旧连接失效（旧连接上此后收到的任何消息与关闭事件都不再影响该账号），再向旧连接发送 `auth.replaced`（E2，“账号已在别处登录”）并以 4002 关闭；对局、匹配与房间随账号转到新连接，与第 3 版带令牌重连的处理相同。

4.2 带 `resume` 的重连与接管走同一条路径；重连令牌只在属于同一账号时有效，换了账号的令牌一律视为找不到。

4.3 登录被撤销时，认证业务在提交后通知联机程序（`onRevoke`，[阶段 6、7 设计](phase6-7.md) 第 5.2 条），按通知的范围关闭连接，收到 `auth.invalid` 并以 4001 关闭：退出只撤销一个会话（通知带 `sessionId`），只关闭以该会话握手的连接，同一账号在别处以其他会话建立的连接不受影响（与账号契约第 3.7 条一致）；修改密码、重置密码撤销该账号的全部会话（通知只带 `userId`），关闭该账号的在线连接。对局中的席位按掉线保留 `GRACE_SECS`，玩家重新登录后在保留期内回来即可继续，否则按掉线判负。

4.4 第 3 版按设备（`uid` 散列）的排位互斥 `queue.ranked-elsewhere` 由一个账号一条连接取代，第 4 版不再下发；按 API-021 该错误码保留不删除。

## 5 段位与对局的归属

5.1 段位、对局记录与段位变化按账号对应的 `users.id` 读写；`RatingStore` 的键由设备散列改为账号的内部编号，开局时记录双方的账号。会员不再写入 `devices` 表。

5.2 升级前的游客段位与棋谱原样保留，不自动并入任何账号；认领按 [阶段 6、7 设计](phase6-7.md) 第 7 章另行实施（下一步计划第 13 章第 2 项）。4.0 起每个账号两种棋均从起始段位开始。

5.3 对局中显示的名字取开局时的雅号；对局中改雅号不影响已开始的对局，与契约第 3.10 条一致。

## 6 错误与提示

6.1 服务端不再下发自然语言文本（API-020）。错误统一为：

```json
{ "t": "error", "code": "room.not-found", "level": "E2", "params": { }, "retryAfterMs": 3000, "errorId": "…" }
```

`params`、`retryAfterMs`、`errorId` 按需出现；`errorId` 只随 E5 下发（API-023）。客户端收到未知错误码时按级别处理，级别也未知时按 E5（API-024）。

6.2 第 3 版以 `info` 下发的操作提示改为 `error`（E1、E2 的操作提示与业务拒绝，例如 `game.not-your-turn`、`game.undo-exhausted`）。不属于错误的服务端通知改为新消息 `notice`：

```json
{ "t": "notice", "code": "server.maintenance" }
```

6.3 `unmatched` 与 `joinNo` 的文本原因改为错误码：

| 消息 | 第 3 版文本 | 第 4 版 |
|---|---|---|
| `unmatched` | 对方未接受 | `reason: "match.declined"` |
| `unmatched` | 对方已离开 | `reason: "match.left"` |
| `unmatched` | 对方未确认（超时） | `reason: "match.unconfirmed"` |
| `unmatched` | （自己拒绝或超时，空串） | 省略 `reason` |
| `joinNo` | 房号不存在，或房间已经开始 等 | `code`：`room.not-found`、`room.own`、`room.already-in`、`room.join-throttled`、`server.maintenance` |

6.4 新增错误码（加入 `src/shared/errors.ts` 与 API 第 8 节，每项有测试）：

| 错误码 | 级别 | 中文原文 | 何时下发 |
|---|---|---|---|
| `auth.replaced` | E2 | 账号已在别处登录 | 第 4.1 条，随 4002 关闭 |
| `match.declined` | E2 | 对方未接受 | 第 6.3 条 |
| `match.left` | E2 | 对方已离开 | 第 6.3 条 |
| `match.unconfirmed` | E2 | 对方未确认 | 第 6.3 条 |
| `game.stale` | E1 | 棋局已更新，请重新操作 | 第 7.3 条，随后发送完整同步 |
| `game.limit-moves` | E2 | 本局已达到 1024 手的上限，按和棋结束 | 第 6.5 条：不单独下发，作为终局原因 `limit-moves` 的说明原文 |
| `game.limit-acts` | E2 | 本局的动作记录已达到 4096 条的上限，按和棋结束 | 第 6.5 条：不单独下发，作为终局原因 `limit-acts` 的说明原文 |

6.5 达到对局上限时，`over` 的终局原因为 `limit-moves` 或 `limit-acts`（`OverReason` 新增两项），排位这一局不结算段位（API-046）；客户端据终局原因显示说明（原文即第 6.4 条的两个错误码），不另发 `notice`；重连时随终局结果补发同样的 `over`。

## 7 状态版本与重同步

7.1 每局有局编号 `match`（服务端本次运行中递增的整数，与日志中的 `gameId` 相同）与状态版本 `sv`（从 0 开始的整数）。服务端每提交一次可观察的对局变更，`sv` 加 1，并在对应的下行消息中带上新的 `sv`：

| 推进 `sv` 的下行消息 | 说明 |
|---|---|
| `start` | 开局，`sv` 为 0，同时带 `match` |
| `moved`、`passed`、`undone`、`marked`、`agreed`、`resumed` | 棋盘、停着、悔棋、点目的变化 |
| `ask`、`answer` | 申请与回应：发给对局双方，见第 7.1.1 条 |
| `over` | 终局 |

`turn`（计时）、`peer`（对方在线状态）、`pong` 不推进版本，也不带 `sv`。

7.1.1 推进 `sv` 的消息都发给对局双方，否则未收到的一方之后的请求会因版本过期而被拒。第 3 版的 `ask` 只发给被申请的一方、`answer` 只发给申请的一方，第 4 版改为双方都收到，并加 `from`（申请方的执子颜色）：

| 消息 | 申请方 | 被申请方 |
|---|---|---|
| `ask` `{ kind, from, sv }` | 申请已送达，等待回应（本地的“待回应”状态以此为准） | 收到申请，显示同意与拒绝 |
| `answer` `{ kind, from, ok, sv }` | 得知结果，清除“待回应” | 清除“收到申请” |

申请超时视为拒绝时同样发 `answer`。

7.2 改变对局状态的上行消息（`move`、`pass`、`undo`、`draw`、`rematch`、`reply`、`resign`、`mark`、`agree`、`resume`、`leave`）带两项：

| 字段 | 规则 |
|---|---|
| `seq` | 本连接上的请求序号，从 1 开始逐条加 1（API-052）；重连或接管后从 1 重新开始；收到完整同步后从其中的 `seq` 加 1 继续（第 7.4 条） |
| `sv` | 发出请求时客户端所知的状态版本 |

7.3 服务端的处理：

| 情况 | 处理 |
|---|---|
| `seq` 小于等于该连接已处理的最大序号 | 视为重复（网络重发），不执行，回复完整同步（第 7.4 条） |
| `seq` 跳号 | 不执行，回复完整同步 |
| `sv` 与当前版本不同（请求所依据的局面已变化） | 不执行，回复 `game.stale`（E1）与完整同步；落子、悔棋等以当前局面为准，不在过期局面上执行 |
| 其余 | 按第 3 版的规则校验并执行 |

7.4 完整同步沿用第 3 版重连时的组合（`start`、`sync`、`agreed`、`over`、`ask`、`turn`），`sync` 增加 `match`、`sv` 与 `seq`，客户端以它们替换本地记录。`seq` 为服务端在该连接上已处理（含按第 7.3 条判为重复或跳号而未执行）的最大请求序号，客户端此后从 `seq` 加 1 继续编号；因而跳号之后只需一次同步即可恢复，不必断开重连。上行新增 `resync`（不带字段），客户端在收到的 `sv` 跳号（丢了下行消息）或局编号与本地不符时发送，服务端回复完整同步；`resync` 受 API-043 的消息限速约束。

7.5 以动作回放（`Act[]`）作为完整同步的内容继续使用：它已覆盖规则配置、棋盘、行棋方、打劫与历史、停着与点目，申请、计时与终局由同一组合中的其他消息补齐。改为单一快照消息须先有等价恢复测试（[阶段 6、7 设计](phase6-7.md) 第 8.3 条），不在本批进行。

## 8 第 3 版客户端

8.1 服务端收到 `v` 不为 4 的 `hello` 时，仍按第 3 版能理解的格式回复，使 3.1 客户端显示可点击的下载提示：先发送一条第 3 版格式的 `welcome`（玩家号 1、随机重连令牌、起始段位，带服务端配置的 `latest` 与 `url`），再发送第 3 版格式的 `{ t: "error", text: "客户端版本与服务器不一致，请更新游戏" }`，然后以 4000 关闭。3.1 客户端收到 4000 不重连（已核对 3.1.0 的 `connection.ts`），并显示“有新版本，点这里下载”。

8.2 这条兼容路径只发送上述三项、不创建玩家、不读写数据库，计入同一 IP 的连接限制；第 3 版的其他消息一律按非法消息处理。它在 4.0 发布满 30 日后可删除，删除时另记修订。

## 9 上线与现有对局

9.1 第 4 版与账号功能必须同时启用：4.0 的服务端要求 `YI_ACCOUNTS=1`，未开启时联机握手一律以 `server.maintenance` 拒绝（第 3.1.1 条），单机不受影响。

9.2 更新服务端会重启进程，进行中的对局本来就会丢失；上线时先按 OPS-045 进入维护模式，等进行中的对局结束再切换，第 3 版对局不迁移到第 4 版。

9.3 数据库无须为本协议新增迁移：账号与 `users.id` 的对应已在结构第 2 版建立，对局与段位表已按 `users.id` 存储。

## 10 逐消息对照

### 10.1 客户端 → 服务端

| 消息 | 第 4 版 |
|---|---|
| `hello` | 第 3.1 条 |
| `ping` | 不变 |
| `name` | 取消；收到时按非法消息处理 |
| `queue`、`unqueue`、`confirm`、`create`、`close`、`join` | 字段不变 |
| `move`、`pass`、`undo`、`draw`、`rematch`、`reply`、`resign`、`mark`、`agree`、`resume`、`leave` | 原有字段之外加 `seq`、`sv`（第 7.2 条） |
| `resync` | 新增（第 7.4 条） |

### 10.2 服务端 → 客户端

| 消息 | 第 4 版 |
|---|---|
| `welcome` | 第 3.2 条：`token` 改名 `resume`，新增 `user` |
| `resumeFailed`、`pong`、`queued`、`found`、`accepted`、`created`、`turn`、`peer`、`left`、`rated` | 不变 |
| `unmatched`、`joinNo` | 原因改为错误码（第 6.3 条） |
